## 결론

### 1. 지금은 둘 다 붙이지 않는다

| 항목 | 결론 | 이유 |
| --- | --- | --- |
| **AI 기억 저장소** | **아무것도 안 붙임** | `Docs/` + git + `CLAUDE.md` + 오토 메모리로 이미 충분하다 |
| **코드베이스 저장소** | **지금은 할 일 없음** | Unity 프로젝트가 아직 없다. 색인할 코드가 없다 |

### 2. 둘은 하나로 합치면 안 된다

Todo 문서에 나란히 적혀 있어서 같은 문제로 보였지만, **성격이 정반대다.**

| | 코드베이스 저장소 | 기억 저장소 |
| --- | --- | --- |
| 만드는 주체 | 파서 — 기계 | AI/사람 — 판단 |
| 무엇이 진짜인가 | **코드가 진짜**, 색인은 사본 | **기억 자체가 진짜** |
| 갱신 | 커밋마다 자동 | 드물게, 손으로 |
| 틀렸을 때 | 다시 파싱하면 고쳐짐 | 손으로 고쳐야 함 |
| **버려도 되나** | **된다** (언제든 재생성) | **안 된다** (날리면 끝) |
| 형태 | 그래프·색인 (기계용) | 마크다운 (사람용) |

코드 색인은 **버려도 되는 캐시**고, 기억은 **버리면 안 되는 원본**이다. 한 저장소에 넣으면 "코드 색인 다시 만들자" 할 때 기억까지 날아간다.

### 3. MCP는 공짜가 아니다 — 이게 판단의 핵심

MCP 서버를 붙이면 **도구 정의가 매 세션 컨텍스트에 들어간다.**

- 서버 5개 × 도구 30개면 첫 메시지 전에 이미 **3만~6만 토큰**이 날아간다
- Anthropic 자신이 도구 정의만 **134,000 토큰**을 먹은 사례를 문서화했다
- 어떤 팀은 도구 정의가 200K 컨텍스트의 **72%** 를 먹어 실작업에 5.7만 토큰만 남았다
- 2026년 공통 인식: **실용적 한계는 서버 5~7개**

**토큰을 아끼고 싶다는 방침과 정면으로 부딪힌다.** 문서 3개짜리 프로젝트에 기억 MCP를 붙이는 건 명백한 손해다.

### 4. 유튜브 링크는 자리를 잘못 잡았다

Todo 문서에서 **기억저장소** 항목 밑에 달린 링크(`ChskqGovoHg`)를 확인해 보니, 실제 내용은 **Graphify** 라는 **코드베이스** 도구 소개였다.

- 영상 : "This Open Source Repo Just Solved Claude Code's #1 Problem" / Chase AI / 2026-06-05
- Graphify : 코드·문서·SQL 스키마를 지식그래프로 바꾸는 도구. 로컬 AST 파싱(tree-sitter), 벡터 스토어 없음
- **기억은 저장하지 않는다.** 코드 구조만 담고 "왜 이렇게 정했나"는 안 남긴다

→ **이 링크는 코드베이스 항목으로 옮기는 게 맞다.**
(영상 자막까지는 확인 못 했다. 제목·설명·소개된 저장소까지만 확인.)

## 1. AI 기억 저장소

### 1-1. Claude Code가 이미 갖고 있는 것

기억이 **두 겹**으로 되어 있다.

| | CLAUDE.md | 오토 메모리 |
| --- | --- | --- |
| 쓰는 주체 | 사람 | Claude 스스로 |
| 내용 | 규칙, 지시 | 알아낸 것, 버릇, 결정 |
| 범위 | 프로젝트/유저/조직 | 저장소 단위 |
| 로드 | 매 세션 전체 | 매 세션 **앞 200줄 또는 25KB** |
| 위치 | `./CLAUDE.md` 등 | `~/.claude/projects/<프로젝트>/memory/` |

- 오토 메모리는 **v2.1.59 (2026-02-26)** 부터 기본 켜짐. 이 프로젝트에도 이미 3건 쌓여 있다.
- `MEMORY.md` 가 목차이고 상세는 토픽 파일로 빠져서 필요할 때만 읽힌다. 전부 평범한 마크다운이라 사람이 열어서 고칠 수 있다.
- `/memory` 로 목록 보기·편집·끄기, `/context` 로 실제 로드된 것 확인.

### 1-2. 빠진 조각과 그 해법

기본 기능의 유일한 구멍은 **"Claude Code 전용이고 머신 로컬"** 이라는 점이다. Gemini CLI 나 로컬 Qwen 이 이 기억을 못 본다.

**해법 제안 (설정 한 줄):** `.claude/settings.json` 에 `autoMemoryDirectory` 를 넣어 저장 위치를 저장소 안으로 옮긴다.

```
"autoMemoryDirectory": "<프로젝트 경로>/Docs/Memory"
```

이렇게 하면:
- 세션이 바뀌어도 이어짐 (원래 되던 것)
- **도구가 바뀌어도 이어짐** — Gemini·Qwen 은 MCP 없이 그냥 마크다운을 읽으면 된다
- 사람이 읽고 고칠 수 있음
- 미니PC ↔ 메인PC 동기화도 git 이 해결

> 이건 조사에서 나온 **제안**이다. 설정 파일 수정은 아직 하지 않았다. 승인해 주시면 적용한다.

### 1-3. 별도 MCP가 필요해지는 지점

딱 세 가지다. **지금은 어디에도 해당하지 않는다.**

1. 다른 도구가 같은 기억을 써야 할 때 → **위 설정으로 해결됨. MCP 불필요**
2. 문서가 **100~300개**를 넘어 grep 으로 못 찾을 때
3. `MEMORY.md` 가 **200줄/25KB 한도**를 계속 넘칠 때 (넘친 부분은 아예 안 읽힘)

지금 이 프로젝트의 문서는 몇 개뿐이고, `Research/` `Design/` `History/` 는 방금까지 비어 있었다. **검색할 게 없는데 검색 엔진부터 다는 격이다.**

### 1-5. 커뮤니티 평가

> "2026년 중반 커뮤니티의 솔직한 평가는, 메모리 서버가 진짜이고 좋아지고 있지만 **잘 관리된 CLAUDE.md 를 이기는 문턱이 출시 홍보보다 훨씬 높다**는 것이다."

- 널리 읽힌 사례: 복잡한 도구를 다 걷어내고 **마크다운 파일 6개**로 돌아갔더니 매 세션 프로젝트를 다시 설명할 일이 없어졌다
- 반복되는 지적: 메모리 서버가 **낡거나 상관없는 맥락을 매 프롬프트에 밀어 넣어 토큰을 낭비한다**
- "context rot" — 오래된 정보가 새 토큰에 묻혀 조용히 잊히는 현상이 2026년 주요 논점

반대편 근거도 있다. basic-memory·Graphify·Beads 는 꾸준히 크고 있다. **다만 인정받는 이유는 "기억을 벡터로 숨겨서"가 아니라 "파일로 눈에 보이게 꺼내놔서"다.**

## 2. 코드베이스 저장소

### 2-1. 지금 할 일은 없다

Unity 프로젝트가 아직 없다. 색인할 코드가 없으므로 **Unity 프로젝트를 만든 다음에 시작한다.**

### 2-2. 1순위 : Serena

| | |
| --- | --- |
| 저장소 | `oraios/serena` |
| 라이선스 | MIT |
| 별 | 28,235 |
| 마지막 push | 2026-08-18 (v1.7.0 / 08-09) |
| 방식 | **LSP 심볼 기반** (임베딩 아님) |

**왜 이걸 고르나**
- **심볼 단위로 답한다.** 파일을 통째로 읽지 않고 "이 함수 정의 어디" / "이거 누가 부르나"를 답한다. **컨텍스트가 작은 로컬 Qwen 에게 이게 결정적이다.**
- 클라이언트를 안 가린다 — Claude Code, Gemini CLI, Codex, VS Code/Cursor, OpenWebUI 전부 지원
- stdio + streamable-http 둘 다 됨
- `serena project index` 로 `.serena/` 에 디스크 캐시를 만든다

**Windows + Unity 주의점 (중요)**
- C# 은 **Roslyn 언어 서버**를 쓰는데 **.NET 10 SDK + PowerShell 7(`pwsh`)** 가 필요하다. **지금 이 PC에 둘 다 없다.**
- Unity C# 프로젝트에서 실제로 터진 이슈가 있다 — issue #537 (Windows 11, MSBuild 타임아웃). **현재 닫혀 있지만** 원인이 "Visual Studio Build Tools 를 못 찾아 폴백"이었다. Unity 를 깔면 보통 같이 깔리니 아마 괜찮겠지만 **직접 돌려봐야 안다.**
- C# 지원은 Serena 에서 손이 많이 가는 언어 축에 든다 (관련 이슈 #359, #384, #513)

### 2-3. 2순위 : codebase-memory-mcp

Serena 의 C#/Windows 설정이 안 풀리면 이쪽.

- MIT, 별 39,535, 2026-08-19 push (아주 활발)
- **의존성 없는 단일 Windows 실행파일** — .NET·PowerShell 7 설치가 필요 없다. 이게 최대 장점
- 여러 클라이언트가 인덱스를 공유하는 구조가 설계에 들어있다
- 단점: 2026년 2월 생성으로 어리고, open issue 469개. **README 주장만 봤고 검증 못 했다**

### 2-4. 인덱스를 어떻게 공유하나

**중앙 서버를 세우지 않는다.** "같은 저장소 + 각자 서버 + 디스크 캐시" 구조다.

```
개발 PC 저장소
  ├─ .serena/           ← 인덱스 캐시 (git 제외)
  ├─ Assets/ ...
  │
  ├─ Claude Code   ──(stdio)──> serena ─┐
  └─ Qwen Code CLI ──(http)───> serena ─┴─> 같은 캐시
```

두 가지 방식 중 **(A)를 권한다.**

- **(A) 코드는 개발 PC에만 두고**, Serena 를 `--transport streamable-http --port 9121` 로 띄워 미니PC 의 Qwen 이 붙는다. **코드 사본이 하나뿐**이라 "누가 옛날 코드를 봤다"는 사고가 안 난다. 단 **방화벽을 로컬 네트워크로 제한할 것.**
- (B) 미니PC 에도 clone 하고 각자 stdio. 간단하지만 git pull 타이밍이 어긋나면 서로 다른 코드를 본다.

### 2-5. 임베딩 RAG는 쓰지 않는다

**심볼 검색이 이긴다.** 근거:

- **Anthropic 이 직접 밝힌 내용**: *"아주 초기에 RAG 를 쓰는 Claude 버전을 시도했다… 결국 agentic search 로 갔다. 그게 다른 모든 걸 압도적으로 앞섰기 때문이다."* Claude Code 는 지금도 코드베이스를 색인하지 않는다.
- 이유: 정확도(grep 은 정확히 맞는 것만, 임베딩은 애매한 오답을 섞음), 색인이 코드와 어긋나지 않음, 청킹 튜닝 불필요, 코드를 밖으로 안 보냄
- **희귀한 식별자(함수명·클래스명) 검색은 BM25/lexical 이 임베딩보다 강하다.** 코드 검색 질문 대부분이 이 유형이다
- 반대 근거(수백만 줄 모노레포)는 있지만 **인디 게임 코드베이스는 그 규모가 아니다**

### 2-6. 직접 만들 값어치가 있는 것 — 딱 하나

`.meta` / `.prefab` / `.unity` 는 YAML인데 **어떤 도구도 이걸 코드로 색인하지 않는다.** 그런데 Unity 에서 "이 스크립트가 어느 프리팹에 붙어 있나"는 GUID 로 풀린다.

1. `Player.cs.meta` 에서 `guid:` 를 읽고
2. `.prefab` / `.unity` 안에서 `m_Script: {fileID: 11500000, guid: <그 guid>}` 를 ripgrep 으로 찾는다

**스크립트 30줄이면 된다.** 자체 제작이 정당화되는 유일한 지점이다.

## 3. 로컬 Qwen 에 MCP 붙이기

**MCP 는 모델이 아니라 클라이언트가 지원해야 한다.** Ollama 자체는 MCP 클라이언트가 아니다.

| 클라이언트 | 형태 | MCP | 평가 |
| --- | --- | --- | --- |
| **Qwen Code CLI** (Apache-2.0, 별 27,190) | 터미널 | stdio·SSE·HTTP 전부 | **1순위.** Qwen 전용 튜닝, 설정이 Claude Code 와 거의 동일 |
| Cline / Roo Code | VS Code 확장 | 지원 | 사람이 화면 보며 쓸 때 |
| LM Studio (0.3.17+) | GUI | 내장 | 손쉬운 검증용 |
| Open WebUI (0.6.31+) | 웹 | `mcpo` 프록시 경유 | stdio 는 프록시 필요 |
| llama.cpp 내장 | 서버 | 2026-03 머지 | 최근 추가 |
| MCPHost | Go CLI | 지원 | **2026-04 아카이브. 쓰지 말 것** |

### 로컬 모델의 MCP 한계 (미리 알아둘 것)

- 작은 모델은 **툴 호출을 놓치거나 JSON 을 깨뜨린다.** 7B는 단일 툴 작업까지, **실용 최소선은 14B 이상**
- **컨텍스트를 반드시 늘려라.** Ollama 기본 4K~8K 면 툴 결과 한 번에 다 찬다. 로컬 코딩 에이전트가 실패하는 **가장 흔한 원인**으로 지목된다. 16K 이상, 가능하면 32K 이상
- **temperature 0.0~0.3.** 높으면 JSON 이 깨진다

## 4. 진행 순서

### 지금 (Unity 프로젝트 전)

1. **기억 저장소** — `autoMemoryDirectory` 설정만 옮긴다. **승인 필요**
2. `AGENTS.md` 참조 표에 `Docs/Memory/` 한 줄 추가 → Gemini CLI 도 읽게 됨
3. Todo 문서의 유튜브 링크를 코드베이스 항목으로 옮긴다
4. **코드베이스 저장소는 아무것도 하지 않는다**

### Unity 프로젝트를 만든 뒤

1. `probe` 로 5분 안에 감을 잡는다 (`install.ps1` 한 줄, 색인 불필요)
2. `.NET 10 SDK` + `PowerShell 7` + `uv` 설치 → Serena 설치 → `serena project index` 로 **Unity 프로젝트가 실제로 로딩되는지 확인**
3. 여기서 막히면 **codebase-memory-mcp(단일 exe)로 갈아탄다**
4. Claude Code 에 먼저 붙여 심볼 검색이 쓸 만한지 확인
5. 미니PC 에 Qwen Code CLI 설치 → 개발 PC 의 Serena 에 HTTP 로 연결. 컨텍스트 32K, temperature 0.2
6. Unity GUID 역참조 스크립트(30줄) 작성

## 5. 확인 못 한 것

- **Serena 가 실제 Unity 프로젝트를 Windows 에서 문제없이 로딩하는지.** 이슈 #537은 닫혔지만 재현·검증 못 했다
- Serena 메모리 문제 (이슈 #944 "~30GB 메모리 소비로 Claude Code 프리즈") — 상태와 원인 확인 못 함
- **codebase-memory-mcp 의 C# 품질과 성능.** README 주장만 봤다. "158개 tree-sitter 문법과 임베딩을 바이너리에 컴파일해 넣었다"는 서술은 크기상 의심스러워 실측이 필요하다
- basic-memory 의 **AGPL-3.0 이 이 프로젝트 결과물에 미치는 법적 영향** — 통설은 있으나 법적 확답 아님
- basic-memory 를 Windows 11 에서 실제로 설치·구동한 결과 (FTS5 이슈 재현 여부)
- 유튜브 영상의 **자막·본문 내용** (제목·업로드일·설명·소개 저장소까지만 확인)
- Gemini CLI 가 `AGENTS.md` 를 직접 읽는지 (`GEMINI.md` 를 컨텍스트 파일로 쓴다는 것만 확인)
- 일부 비교 글(rywalker.com, sverklo.com)은 **자사 제품이 목록에 포함된 마케팅성 글**이라 수치를 신뢰하기 어렵다. 독립 검증본을 못 찾았다
- reddit 은 크롤링이 막혀 커뮤니티 원문을 직접 못 읽었다. 기술 블로그 인용을 통한 간접 확인이다
