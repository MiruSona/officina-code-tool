# 코드 컨벤션 조사

> 조사일 2026-08-20 · 대상 : 로컬 LLM(Qwen)에게 넘긴 Unity C# 코드를 **합격/불합격 판정**하는 기준 만들기
> 이 문서는 조사 결과다. 실제 컨벤션 문서는 아직 안 만들었다.

---

## 결론 먼저

### 1. 컨벤션 문서는 두 개로 쪼갠다

| 문서 | 내용 | 분량 | 읽는 쪽 |
| --- | --- | --- | --- |
| `Guide/코딩컨벤션.md` | 왜 이렇게 정했는지 + 전체 규칙 | 제한 없음 | 사람, Claude |
| `Guide/코딩컨벤션-요약.md` | 로컬 LLM 이 매번 읽는 1페이지 | **규칙 12~15개, 100줄 이내** | 로컬 Qwen |

**로컬용 요약본에는 기계가 잡을 수 있는 규칙을 아예 안 쓴다.** 들여쓰기, 중괄호 위치, 공백 같은 건 포맷터가 고쳐 준다. 문서에 쓰면 규칙 개수만 늘어나서 정작 중요한 규칙이 묻힌다. (근거는 5장)

### 2. 기계가 잡는 것 / 문서에 쓸 것 — 이 경계가 이번 조사의 핵심

| 항목 | 누가 잡나 | 문서에 쓰나 |
| --- | --- | --- |
| 들여쓰기, 줄바꿈, 중괄호 위치, 공백, 줄 길이 | **CSharpier** (자동 고침) | ❌ 안 쓴다 |
| `using` 정렬·제거, `var` 사용, 표현식 본문 | **.editorconfig + dotnet format** | ❌ 안 쓴다 |
| 이름 규칙 (PascalCase / camelCase / `_` / `I` 접두사) | **.editorconfig 이름 규칙** | ❌ 안 쓴다 (단, Unity 안 검증은 6장 주의) |
| Unity 함정 43종 (`GetComponent` 남발, `Time.deltaTime` 오용, 태그 비교, 코루틴 반환값 무시 …) | **Microsoft.Unity.Analyzers** (공짜, 자동 포함) | ❌ 안 쓴다 |
| 쓰면 안 되는 API 목록 (`GameObject.Find`, `Camera.main` 등) | **BannedApiAnalyzers** (설정 파일에 적기만) | ❌ 안 쓴다 |
| **이름을 무엇으로 지을지** (뜻·단어 선택) | 아무도 못 잡는다 | ✅ **예제로 쓴다** |
| **파일·폴더·어셈블리 배치** | 일부만 (asmdef) | ✅ 쓴다 |
| **MonoBehaviour 에 로직을 얼마나 넣나, 상태를 어디에 두나** | 못 잡는다 | ✅ 쓴다 |
| **어떤 방식을 쓸지** (ScriptableObject vs static, 이벤트 vs 직접 호출) | 못 잡는다 | ✅ 쓴다 |
| **에러 처리·로그 방침, 주석 방침, 테스트 범위** | 못 잡는다 | ✅ 쓴다 |

> 한 줄 요약 : **"틀리면 빨간 줄이 뜨는 것"은 문서에서 뺀다. "틀려도 컴파일은 되는 것"만 문서에 남긴다.**

### 3. 뼈대로 삼을 자료 — Microsoft 것 하나면 된다

- **Microsoft C# 코딩 컨벤션** (`dotnet/docs`) — **CC-BY-4.0**. 우리 라이선스 조건에 맞고, 그대로 베껴 써도 된다(출처만 표기). 이게 사실상 표준이다.
- **Unity C# 스타일 가이드 e-book (2025년 2판, Unity 6 판)** — Unity 스스로 *"Microsoft Framework Design Guidelines 를 확장한 것"* 이라고 밝힌다. 즉 **내용이 겹친다.** 읽고 참고는 하되 **문장을 베끼지 않는다** (라이선스가 CC/MIT 계열이 아니다).
- **Kodeco(구 raywenderlich) C# 스타일 가이드** — MIT 인데 *"프로그래밍 교육용 저작물에는 못 쓴다"* 는 조항이 붙어 있다. 게다가 **마지막 갱신이 2023-02** 다. **쓰지 말자.**

### 4. 자동 검증은 3층으로 쌓는다

| 층 | 도구 | 라이선스 | 잡는 것 | 판정 방법 |
| --- | --- | --- | --- | --- |
| 1 | **CSharpier** | MIT | 모든 서식 | `dotnet csharpier check .` → 안 맞으면 종료코드 1 |
| 2 | **Microsoft.Unity.Analyzers** | MIT | Unity 특유의 실수 43종 | Unity 컴파일 시 경고/에러 |
| 3 | **.globalconfig** | — | 위 규칙들의 심각도(에러/경고/무시) | Unity 안에서도 먹힌다 |

**CSharpier 를 1순위로 미는 이유** : `.csproj` 나 솔루션 없이 **폴더만 지정해도 돈다.** Unity 는 `.csproj` 를 수시로 다시 만들기 때문에, MSBuild 에 의존하는 `dotnet format` 보다 스크립트로 묶기가 훨씬 쉽다. `format.ps1` 이 바로 이거 한 줄이면 된다.

### 5. SOLID — 5개 중 2개만 쓴다

우리 프로젝트는 **2D 탑다운, 64×64 픽셀, 1인+AI 스튜디오** 다. 이 규모에서 SOLID 를 전부 적용하면 손해다.

| 원칙 | 우리 방침 | 이유 |
| --- | --- | --- |
| **S** (한 가지 일만) | ✅ **쓴다** — 단 "클래스 하나 = 기능 하나" 수준까지만 | 로컬 LLM 은 파일이 클수록 엉뚱한 데를 고친다. 작은 파일이 곧 안전장치다 |
| **O** (고치지 말고 늘려라) | ⛔ 안 쓴다 | 기획이 안 정해졌다. 미리 확장점을 만들면 대부분 헛수고다 |
| **L** (자식은 부모 자리에 들어가야) | ➖ 상속을 거의 안 쓸 거라 자동으로 지켜진다 | Unity 는 상속보다 컴포넌트 조합이 기본이다 |
| **I** (인터페이스는 잘게) | ⛔ 안 쓴다 | 인터페이스 자체를 거의 안 만든다 |
| **D** (구체가 아니라 약속에 의존) | ✅ **축소판만** — "다른 MonoBehaviour 를 `GameObject.Find` 로 찾지 말고 `[SerializeField]` 로 받아라" 정도 | 이건 실제로 버그를 막는다. DI 프레임워크는 안 쓴다 |

**반론도 근거가 확실하다.** Casey Muratori 는 "clean code" 규칙 5개 중 4개(다형성 우선, 내부를 몰라야 함, 함수는 작게, 함수는 한 가지만)가 성능을 **10~25배**까지 깎는다고 실측을 냈다. 게임 업계에서 데이터 지향 설계(DOD)가 힘을 얻은 이유다. 다만 반박도 있다 — "느려지는 건 추상화 자체가 아니라 **나쁜 추상화**이고, 문제는 빡빡한 루프 안에서만 생긴다"는 것이다.

우리 결론 : **빡빡한 루프(Update, 물리, 렌더)에는 추상화를 넣지 않는다. 그 밖에는 읽기 쉬운 쪽을 고른다.** ECS/DOTS 는 이 규모에 필요 없다.

### 6. 기성 스킬·MCP — 쓸 만한 게 없다. 직접 만든다

- **Anthropic 공식 스킬 저장소(`anthropics/skills`)에 코드 컨벤션 스킬이 없다.** (19개 스킬 전부 확인)
- 컨벤션·리뷰용 MCP 서버도 쓸 만한 게 없다 (`mcp-lint-tools` : ⭐0).
- 게임 개발용 스킬 모음은 있지만(`gamedev-skills/awesome-gamedev-agent-skills`, Apache-2.0, ⭐554) **컨벤션 스킬이 아니라 "Unity C# 작성법" 스킬**이다. 다만 **문서 형태의 본보기로는 아주 좋다** (7장 참고).
- → **컨벤션 스킬은 우리가 직접 쓴다.** 어차피 우리 규칙이라 남의 걸 가져다 쓸 이유가 없다.

## 3. 자동 검증 수단 — 무엇을 어디까지 기계가 판정할 수 있나

### 3-1. Unity 의 Roslyn analyzer 지원 — 된다. 단 함정이 있다

**되는 것 (Unity 공식 문서로 확인)**
- analyzer `.dll` 을 `Assets/` 아래에 넣고, Plugin Inspector 에서 플랫폼을 전부 끄고, **`RoslynAnalyzer` 라벨**을 붙이면 Unity 가 컴파일할 때 같이 돈다.
- **범위 지정** : analyzer 가 `.asmdef` 가 있는 폴더 안에 있으면 그 어셈블리(및 그걸 참조하는 어셈블리)에만 적용된다. `Assets/` 루트에 두면 전체에 적용된다.
- **심각도 조절** :
  - `.ruleset` 파일 — `Assets/Default.ruleset`(전체), `Assembly-CSharp.ruleset`(특정 어셈블리). 값은 `Error` / `Warning` / `Info` / `None`.
  - **`.globalconfig` 파일** — Unity 2021.3부터 되고 Unity 6에서 정식 문서화. 맨 위에 `is_global = true` 를 쓰고 진단 ID별 심각도를 적는다. `Assets/Default.globalconfig` 또는 `.asmdef` 옆에 둔다. **Unity 가 생성하는 `.csproj` 에 `GlobalAnalyzerConfigFiles` 로 들어가서 IDE 와 Unity 가 같은 설정을 본다.** ← 이게 지금 가장 깔끔한 방법이다.

**안 되는 것 (⚠️ 중요)**
- **`.editorconfig` 는 Unity 에디터 컴파일에서 무시된다.** Unity 이슈 트래커에 등록됐고 **"Won't Fix"(안 고침)로 닫혔다.** 2022.3 이후로는 "에디터에서 analyzer 끄기" 옵션까지 없어져서 더 나빠졌다.
- 즉 `.editorconfig` 로 정한 이름 규칙·서식 규칙은 **IDE(Rider/VS)와 `dotnet` 명령줄에서는 먹지만, Unity 안에서는 안 먹는다.**

**그래서 이렇게 나눈다**

```
.editorconfig      → IDE 와 dotnet format / CSharpier 용 (Unity 밖 검증)
.globalconfig      → Unity 에디터 컴파일 시 심각도 조절용 (Unity 안 검증)
```

### 3-2. Microsoft.Unity.Analyzers — 공짜로 얻는 가장 큰 이득

- 저장소 : https://github.com/microsoft/Microsoft.Unity.Analyzers · **MIT** · ⭐810 · **2026-08-18 갱신** (아주 활발)
- **Visual Studio 의 "Unity 게임 개발" 워크로드에 기본 포함**되고, **VSTU 4.3.2.0 부터는 Unity 가 생성하는 모든 `.csproj` 에 자동으로 들어간다.** 즉 **설치 없이 이미 돌고 있을 가능성이 높다.**
- **진단 43종(UNT0001~UNT0043)** : 빈 Unity 메시지, 비효율 태그 비교, 제네릭 아닌 `GetComponent`, `Update` 에서 `Time.fixedDeltaTime` 사용, Unity 객체에 `??`/`?.` 사용, 코루틴 반환값 무시, 잘못된 `SerializeField`, `Update` 안의 리플렉션, `WaitForSeconds` 캐시 안 함, 반복 호출에 `Animator.StringToHash` 미사용, 조건부 컴파일 심볼 오타 등.
- **억제기 23종(USP0001~USP0023)** : 일반 C# 규칙이 Unity 에서 오탐하는 걸 꺼 준다. 예를 들어 `USP0023` 은 **`IDE1006`(이름 규칙)이 `Start`/`Update` 같은 Unity 메시지를 잡는 걸 막아 준다.**
  → **이름 규칙을 기계로 강제하려면 이 analyzer 가 사실상 필수다.** 없으면 Unity 메시지가 전부 위반으로 잡힌다.

**이게 왜 중요한가** : 로컬 LLM 이 Unity 코드에서 저지르는 실수의 상당수(`Update` 안 `GetComponent`, `null` 비교, 태그 비교, 코루틴 실수)가 **여기서 이미 자동으로 잡힌다.** 컨벤션 문서에 "Update 안에서 GetComponent 하지 마라"를 쓸 필요가 없다는 뜻이다.

### 3-3. CSharpier — 서식 판정기

- 저장소 : https://github.com/belav/csharpier · **MIT** · ⭐2,301 · **v1.3.0 (2026-06-07)**, 2026-08-19 갱신
- Prettier 를 C# 으로 옮긴 것. **옵션이 거의 없다** — 옵션을 늘릴 계획도 없다고 못 박았다. 이게 우리한테는 장점이다. **논쟁할 여지가 없으면 로컬 LLM 이 틀릴 여지도 없다.**
- `dotnet csharpier format <폴더>` : 폴더를 재귀적으로 고친다. **`.csproj` / 솔루션이 필요 없다.**
- `dotnet csharpier check <폴더>` : 안 맞는 파일을 출력하고 **종료 코드 1** 을 낸다 → `format.ps1` 의 합격 판정에 그대로 쓴다.
- `.csharpierrc` / `csharpier.yaml` / `.editorconfig` 로 설정, `.csharpierignore` 로 제외.

### 3-4. dotnet format

- .NET SDK 에 들어 있다. `.editorconfig` 를 읽는다.
- **`--verify-no-changes` 를 붙이면 고치지 않고 검사만 하고, 고칠 게 있으면 0이 아닌 종료 코드를 낸다.** → 기계 판정에 쓸 수 있다.
- 하위 명령 : `dotnet format whitespace`(서식), `dotnet format style`(코드 스타일 규칙 = 이름 규칙 포함), `dotnet format analyzers`(analyzer 규칙).
- **단점** : MSBuild 프로젝트가 필요하다. Unity 는 `.csproj` 를 자산이 바뀔 때마다 다시 만들고, 복원(restore)이 깨지는 사례가 알려져 있다. → **CSharpier 를 1순위, dotnet format 을 2순위로 둔다.**

### 3-5. StyleCop.Analyzers

- 저장소 : https://github.com/DotNetAnalyzers/StyleCopAnalyzers · **MIT** · ⭐2,854
- **규칙 195개.** 마지막 정식 릴리스는 `1.1.118`, 그 뒤로는 `1.2.0-beta.556`(**2023-12**)에서 멈춰 있다. 커밋은 2025-12 까지 있다 → **살아 있지만 느리다.**
- 설정은 `.editorconfig` 가 아니라 **자체 형식(`stylecop.json`)** 을 쓴다. Unity 와 궁합이 나쁘다. Unity 에 붙이려면 `Directory.Build.props` 로 우회해야 하고, 예전 우회법(`OnGeneratedCSProject` 훅)은 Unity 2021.1 에서 없어졌다.
- **판정 : 쓰지 말자.** 규칙 195개는 우리 규모에 과하고, CSharpier 가 서식을 자동으로 고쳐 주면 StyleCop 이 잡을 게 거의 안 남는다.

### 3-6. BannedApiAnalyzers — "하지 마라" 목록을 기계에게 넘기는 방법

- NuGet : `Microsoft.CodeAnalysis.BannedApiAnalyzers` · **MIT** · **v5.6.0 (2026-07-02)** · 누적 4,360만 다운로드 (.NET Runtime, MAUI, Jellyfin 등에서 사용)
- 텍스트 파일에 금지할 API 를 적어 두면 쓰는 순간 진단이 뜬다.
- **우리에게 딱 맞는 용도** : `GameObject.Find`, `Camera.main`, `SendMessage`, `Object.FindObjectOfType` 같은 걸 금지 목록에 넣으면, **"이거 쓰지 마라"를 문서가 아니라 컴파일러가 말해 준다.**
- ⚠️ **주의** : Unity 는 analyzer 설정 파일을 `Filename.[AnalyzerName].additionalfile` 이라는 이름 규칙으로만 넘긴다. BannedApiAnalyzers 는 `BannedSymbols.txt` 라는 고정 이름을 기대해서 **이름이 안 맞을 수 있다.** (일본어 기술 블로그에서 이 문제를 지적) → **실제로 되는지 확인 필요.**

### 3-7. 정리 — `format.ps1` / `build.ps1` 이 판정할 수 있는 범위

```
합격 판정 = (1) AND (2) AND (3)

(1) dotnet csharpier check ./Assets/Scripts     → 서식
(2) Unity 배치 모드 컴파일 에러 0                → 문법 + Unity analyzer 43종 + 금지 API
(3) Unity Test Runner 통과                       → 동작
```

**여기서 판정 못 하는 것** = 이름의 뜻, 파일 배치, 설계 방향, 주석 품질. **이게 곧 컨벤션 문서에 남길 내용이다.**

## 4. SOLID — 어디까지 쓸 것인가

### 찬성 쪽

- **Unity 공식 e-book** 『Level up your code with design patterns and SOLID』(Unity 6판, Asset Store 에 예제 프로젝트 포함). 패턴 11종(Factory, Object Pooling, Singleton, Command, State, Observer, MVP, MVVM, Strategy, Flyweight, Dirty Flag)과 SOLID 예제를 다룬다. Unity Learn 에 『Design Patterns (Unity 6)』 강의도 있다.
- gamedeveloper.com 「SOLID Principles for Game Developers」 — 게임 개발자들에게 SOLID 가 잘 안 알려져 있지만 적용할 수 있다는 입장.

### 반대 쪽 (근거가 약하지 않다)

**Casey Muratori, "Clean Code, Horrible Performance" (2023-02-28)**
- 『Clean Code』 규칙 5개 중 **4개가 성능을 크게 깎는다**고 실측:
  - 다형성 대신 switch → **1.5배** 빠름
  - switch 대신 표 기반 → **10배**
  - 속성 하나 추가 시 → **15배**
  - AVX 최적화까지 → **20~25배**
- 그의 표현 : *"clean code 개념의 처음 두 규칙이 하드웨어 12년치 발전을 날려 버린다."*
- 5개 중 DRY(중복 제거)만 조건부로 인정했다.

**Mike Acton, CppCon 2014 「Data-Oriented Design and C++」** — 흔한 개발 방법론이 성능 나쁜 소프트웨어를 만든다는 게임 업계의 대표적 반론. Unity DOTS/ECS 가 이 흐름에서 나왔다.

**Unity 컴포넌트 지향 자체가 SOLID 와 다른 축이다**
- Unity 는 상속이 아니라 **조합(컴포넌트)** 이 기본이라 L(리스코프)·I(인터페이스 분리)를 쓸 일이 별로 없다.
- 대신 컴포넌트 방식의 고유한 함정이 있다 : **너무 잘게 쪼갠 스크립트**(관리 비용이 코딩 비용을 넘음), **숨은 의존**(`GetComponent<Rigidbody>()` 로 조용히 다른 컴포넌트를 기대함).

### 반대의 반대 (균형)

**Evan Teran, "Casey Muratori is wrong about clean code (but he's also right)" (2023-04)**
- Muratori 가 비판한 건 **추상화 자체가 아니라 나쁜 추상화**다.
- *"Casey 의 코드조차 그가 지적한 clean code 원칙 대부분을 어기지 않는다."*
- 빡빡한 루프 안의 가상 함수와 힙 할당(캐시 지역성 파괴)은 진짜 문제지만, `std::variant` + `std::visit` 는 수동 switch 보다 **2.5배 빠른** 경우도 있었다. → **"프로파일링하라"가 결론.**
- Muratori 의 표 기반 해법은 컴파일 타임 상수 접기 덕이 크다 → **다른 문제를 푼 것**이다.

### Unity 커뮤니티의 실무 감각

Unity 공식 포럼 「"How much" should you apply SOLID principles?」 요약 :
- **"원칙이지 규칙이 아니다. 필요한 데 쓰고, 필요 없는 데 쓰지 마라."**
- **"원칙 적용은 투자다. 지금 시간을 더 쓰는 대신 나중에 시간을 아낄 거라 믿을 때만 해라."**
- 구현체가 하나뿐인데 인터페이스를 만드는 건 복잡도만 늘린다.
- DI 프레임워크는 유효하지만 인디에겐 대체로 과하다.
- **"프로젝트와 함께 구조를 키워라. 복잡해진 곳에만 구조를 넣어라."**

### 우리 방침 (다시)

| 원칙 | 방침 |
| --- | --- |
| **S** | 쓴다. 단 **"파일 하나 = 클래스 하나 = 기능 하나"** 수준. 이유는 설계 미학이 아니라 **로컬 LLM 안전** — C# 패치는 평균 4.88개 파일에 걸치고(SWE-Sharp-Bench), 로컬 모델은 "어디를 고칠지"를 가장 많이 틀린다 |
| **O** | 안 쓴다 |
| **L** | 상속을 거의 안 쓰므로 해당 없음 |
| **I** | 안 쓴다 |
| **D** | **`[SerializeField]` 로 의존을 명시하고, `GameObject.Find`/`FindObjectOfType` 를 금지**하는 선까지만. DI 프레임워크 없음 |

**추가 규칙 하나** : `Update`/`FixedUpdate`/`LateUpdate` 안에서는 인터페이스 호출·LINQ·할당을 피한다. (Muratori/Acton 쪽 근거)

## 5. AI, 특히 작은 로컬 모델이 실제로 지킬 수 있는 문서 형태

### 5-1. 규칙 개수가 많을수록 지키는 비율이 떨어진다 — 측정된 사실

**「How Many Instructions Can LLMs Follow at Once?」 (arXiv:2507.11538, 2025-07-15)**
- IFScale 벤치마크 : 지시를 1개부터 500개까지 늘리면서 준수율을 잰다.
- 7개 업체 20개 모델 측정. **최고 성능 모델조차 지시 500개에서 정확도 68%.**
- **모델 크기와 추론 능력에 따라 성능 저하 패턴이 3가지로 갈린다** → **작은 로컬 모델일수록 더 빨리 무너진다.**
- **앞쪽 지시에 치우친다(primacy bias).** → **가장 중요한 규칙을 문서 맨 위에 둬야 한다.**

**이 프로젝트에 적용하면**
- 규칙 개수 = 지시 개수다. **서식 규칙 20개를 문서에 넣으면 정말 중요한 규칙 10개의 준수율이 같이 떨어진다.**
- 그래서 서식은 포맷터에게 넘기고 문서에서 빼는 게 **취향이 아니라 성능 문제**다.
- 규칙 순서 : ① 파일·시그니처 제약 → ② 이름 → ③ Unity 사용법 → ④ 나머지.

### 5-2. Anthropic 공식 스킬 작성 지침

`anthropics/skills` 의 `skill-creator` 스킬에서 직접 확인 :
- 메타데이터(name + description) : **약 100 단어** — 항상 문맥에 올라간다
- SKILL.md 본문 : **500줄 이내가 이상적**
- *"500줄에 가까워지면 계층을 하나 더 만들고, 모델이 다음에 어디를 봐야 할지 분명히 가리켜라."*
- 참조 파일이 300줄을 넘으면 목차를 붙여라

→ **500줄은 Claude 급 모델 기준이다.** 로컬 30B 급에는 훨씬 더 짧아야 한다. **100줄 이내를 목표로 잡는다.** (이 숫자는 위 자료의 직접 근거가 아니라 우리 판단이다.)

### 5-3. "예제 중심" 결론 — 뒷받침되지만, 그대로는 위험하다

**뒷받침하는 근거**
- 잘 만들어진 실제 스킬(`unity-csharp-scripting`, Apache-2.0)의 구조 : **SKILL.md 6.2KB**. 규칙을 산문으로 늘어놓지 않고 **"목적별로 콜백을 골라라" 같은 한 줄 + 바로 밑에 주석 달린 코드 블록** 형태다. 지금 실무에서 통하는 형태가 이거다.
- 「Does Few-Shot Learning Help LLM Performance in Code Synthesis?」(arXiv:2412.02906) : 예제를 잘 고르면 **CodeLlama 의 HumanEval+ 점수가 뚜렷이 오른다.** → 코드 작업에서 예제는 효과가 있다. 단 **"잘 고른" 예제**여야 한다.

**뒤집는 근거 (⚠️ 반드시 반영할 것)**
- 「Beyond "To whom it may concern"」(arXiv:2606.03259, 2026-06) : 모델 크기 5종에서 **"명시적 지시가, 의미가 맞춰진 few-shot 예제보다 낫다"** 는 결과가 나왔다.
  - 단 이건 **기계 번역** 과제다. 코드 스타일이 아니다. **그대로 옮기면 안 된다.**
  - 그래도 시사점은 분명하다 — **예제만 던지면 모델이 "무엇을 따라 하라는 건지"를 잘못 고를 수 있다.**

**그래서 수정된 결론**

> **"예제만"이 아니라 "규칙 한 줄 + 바로 밑에 좋은 예/나쁜 예 코드 한 쌍"** 이 가장 안전하다.
> 규칙 문장은 **무엇을 따라 해야 하는지 범위를 정해 주고**, 예제는 **애매함을 없앤다.** 둘 중 하나만 있으면 각각의 약점이 그대로 남는다.

기존 프로젝트 결론("'하지 마라' 목록보다 '이렇게 써라' 코드 예제 3개가 잘 먹힌다")은 **절반만 맞다.** 예제가 중요한 건 맞지만, **규칙 문장을 빼면 안 된다.**

### 5-4. 문서보다 린터가 낫다 — 업계 쪽 근거

**Factory.ai, "Using Linters to Direct Agents" (2025-09-05)**
- *"에이전트에게는 구체적으로 검증할 수 있는 규칙이 필요하다. 제안이 아니라 린트 규칙이 필요하다."*
- 마크다운 규칙 문서(`AGENTS.md`)의 약점 3가지 :
  1. **모호함** — 자연어는 예외를 허용해서, 에이전트가 "지켰다"고 착각한다
  2. **강제력 없음** — *"조언은 빌드를 실패시키지 않는다. 그래서 어긋남이 조용히 쌓인다"*
  3. **범위 한계** — 산문으로는 파일 간 import, 구조 경계, 에러 처리 패턴을 검증할 수 없다
- 린트 규칙의 장점 : 에이전트가 **"초록불이 될 때까지 스스로 고친다."**
- ⚠️ 이 글은 **수치 데이터가 없다.** 주장이지 측정이 아니다.

**PyTorch AI 코딩 플레이북 (2026-05-30)** : 하위 시스템별 기준으로 diff 를 평가하는 **AI 린터를 만들 계획**이라고 밝혔다. → 방향은 같지만 **아직 계획 단계**다.

### 5-5. 블로그에서 도는 숫자들 — 참고만 (검증 안 됨)

여러 2026년 블로그에서 공통적으로 나오는 주장들이다. **연구 근거가 아니라 경험담이다. 그대로 믿지 말 것.**
- CLAUDE.md 가 200줄을 넘으면 가운데 내용이 사실상 사라진다
- Cursor 는 앞쪽 ~50줄만 안정적으로 읽고, 80줄쯤에 있는 규칙은 자주 건너뛴다
- 항상 적용되는 규칙은 합쳐서 2,000 토큰 아래로 유지하라
- "깨끗한 코드를 써라" 같은 규칙은 아무 효과가 없다. **검증 가능한 규칙**이어야 한다
- 규칙에 **"왜"** 를 붙이면 비슷한 상황으로 일반화된다

이 중 **"검증 가능한 규칙"** 과 **"왜를 붙여라"** 는 위 학술 근거(IFScale 의 primacy bias, Factory.ai 의 모호함 지적)와 방향이 맞으므로 채택할 만하다. 줄 수 숫자는 근거가 없다.

## 6. 제안하는 문서 뼈대 (다음 설계 단계 입력)

### `Guide/코딩컨벤션-요약.md` (로컬 LLM 용, 100줄 이내)

```
0. 이 문서를 어길 수 없는 것 (맨 위 = 가장 잘 지켜짐)
   - 지시서에 적힌 파일만 건드린다
   - 지시서에 적힌 시그니처를 그대로 쓴다
   - 새 파일을 만들지 않는다

1. 이름   (규칙 4개 + 예제 표 1개)
```

## 7. 확인 못 한 것

- **Unity 버전이 안 정해졌다.** `.globalconfig` 지원(2021.3+), analyzer 범위 규칙은 Unity 6 문서 기준으로 조사했다. 버전이 정해지면 다시 봐야 한다.
- **Unity e-book 본문을 직접 못 읽었다.** `unity.com` 이 봇 접근을 막는다(HTTP 403). 공식 포럼 공지와 검색 결과로만 확인했다. **PDF 를 사람이 직접 받아서 확인해야 한다.**
- **Unity e-book 의 정확한 사용 약관을 못 봤다.** "Unity Companion License" 는 Unity 패키지용이고 e-book 에도 적용되는지 확인 못 했다. → **e-book 문장을 베끼지 않으면 문제 없다.**
- **`.editorconfig` 의 이름 규칙(`dotnet_naming_rule`)을 Unity 밖에서 어떻게 기계 판정할지 확정 못 했다.** `dotnet format style --verify-no-changes` 가 Unity 가 생성한 `.csproj` 에서 실제로 도는지 안 해 봤다. CSharpier 는 이름 규칙을 안 잡는다.
- **BannedApiAnalyzers 가 Unity 안에서 실제로 도는지 확인 못 했다.** Unity 의 `.additionalfile` 이름 규칙과 안 맞을 수 있다는 지적만 봤다.
- **Microsoft.Unity.Analyzers 가 Rider 에서도 자동 포함되는지 확인 못 했다.** README 는 Visual Studio 와 VS Code 확장만 언급한다.
- **`.ruleset` 과 `.globalconfig` 를 같이 두면 어느 쪽이 이기는지** 확인 못 했다.
- **로컬 Qwen 이 실제로 규칙 몇 개까지 지키는지 안 재 봤다.** IFScale 은 우리 모델·우리 과제가 아니다. **미니PC 도착 후 골든 테스트로 직접 재야 한다.**
- **"규칙 12~15개, 100줄"은 우리 판단이지 측정값이 아니다.** IFScale 이 "많을수록 나빠진다"를 보였을 뿐, 임계값을 준 게 아니다.
- **GitHub 검색의 별 개수가 신뢰하기 어렵다.** 스킬 저장소들의 별 개수가 비정상적으로 크다. 라이선스와 갱신일만 판단에 썼다.
- **아무것도 실제로 설치·실행해 보지 않았다.** 전부 문서와 저장소 메타데이터 기준이다.
- WebSearch 는 이번 조사에서 정상 작동했다. 다만 `unity.com` 과 `mcpmarket.com` 은 봇 차단(403/429)으로 못 열었다.

## 8. 사용자에게 물어볼 것

1. **Unity 버전과 렌더 파이프라인을 언제 정할 것인가?** 컨벤션 문서의 상당 부분(analyzer 설정 방식, `.globalconfig` 지원)이 여기 걸려 있다. **Unity 6 LTS 로 가정하고 먼저 써도 되나?**
2. **CSharpier 를 도입해도 되나?** MIT, .NET 도구. `AGENTS.md` 7번(라이브러리·패키지 추가는 승인 필요)에 걸린다. 도입하면 서식 규칙을 문서에서 전부 뺄 수 있다.
3. **서식을 "AI 가 알아서" 대신 "포맷터가 강제로 고침"으로 바꿔도 괜찮은가?** CSharpier 는 옵션이 거의 없어서 **개인 취향(중괄호 위치 등)을 못 바꾼다.** 대신 논쟁이 사라진다. 취향보다 자동화를 택할 건지 확인 필요.
4. **SOLID 를 "S 와 D 축소판만" 으로 좁히는 데 동의하나?** Unity 공식 e-book 은 패턴 11종을 다 가르치지만, 우리 규모(2D 탑다운, 64×64)에는 과하다고 판단했다.
5. **금지 API 목록을 어디까지 넣을 것인가?** 예: `GameObject.Find`, `FindObjectOfType`, `Camera.main`, `SendMessage`, `Update` 안의 LINQ. **`Camera.main` 은 Unity 2020 이후 캐시되므로 굳이 막을 필요 없다는 반론도 있다.**
6. **컨벤션을 Claude Code 스킬로 만들 것인가, 그냥 문서로 둘 것인가?** 로컬 Qwen 은 스킬을 못 읽으니 **어차피 로컬용 축약 문서는 따로 필요하다.** 스킬은 Claude 쪽 리뷰용으로만 의미가 있다.
7. **테스트 프레임워크를 Unity Test Framework 로 갈 것인가?** 합격 기준(`test.ps1`)이 여기 걸린다.
