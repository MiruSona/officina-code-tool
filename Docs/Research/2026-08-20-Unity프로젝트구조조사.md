조사일 : 2026-08-20
대상 : 스튜디오 저장소의 AI 게임 스튜디오 할 일 문서에 있던 "Unity 환경 게임 프로젝트 구조 설계를 위한 스킬 또는 괜찮은 설계"
전제 : **2D 탑다운**, **1인 + AI**, Unity 프로젝트 본체는 아직 없음, 코드 검색은 **Serena(LSP 심볼)** 예정

## 결론 먼저

### 1. 권장 폴더 구조

```
ProjectOfficina/                  ← git 저장소 뿌리 (지금 그대로)
├─ Docs/                          ← 문서 (지금 그대로)
├─ Tools/                         ← 2D 그림 툴 · 사운드 툴 · MCP 툴 (C# 아님)
├─ AGENTS.md  CLAUDE.md  GEMINI.md
└─ Unity/                         ← ★ Unity 프로젝트는 여기 안에
   ├─ .gitignore                  ← 지금 뿌리에 있는 Unity.gitignore 를 여기로 옮김
   ├─ Packages/
   ├─ ProjectSettings/
   └─ Assets/
      ├─ _Project/                ← 우리가 만든 것만 (밑줄로 맨 위 고정)
      │  ├─ Art/
      │  │  ├─ Sprites/           ← 캐릭터·오브젝트 스프라이트
      │  │  ├─ Tiles/             ← 타일맵·타일 팔레트
      │  │  └─ UI/
      │  ├─ Audio/
      │  │  ├─ BGM/
      │  │  └─ SFX/
      │  ├─ Data/                 ← ScriptableObject 에셋 (수치·설정)
      │  ├─ Prefabs/
      │  ├─ Scenes/
      │  ├─ Settings/             ← 렌더 파이프라인·인풋 설정
      │  └─ Scripts/
      │     ├─ Officina.Runtime.asmdef
      │     ├─ Core/              ← 부트스트랩, 공통 유틸, 이벤트 정의
      │     ├─ Gameplay/
      │     │  ├─ Player/
      │     │  ├─ Enemy/
      │     │  └─ World/
      │     ├─ UI/
      │     └─ Editor/
      │        └─ Officina.Editor.asmdef
      └─ Plugins/                 ← 남이 만든 것 (에셋스토어·UPM 아닌 것)
```

**핵심 원칙 세 개**

| 원칙 | 내용 |
| --- | --- |
| **그림·소리는 유형별, 코드는 기능별** | 스프라이트는 `Art/Sprites/` 한곳에 모으고, 코드는 `Scripts/Gameplay/Player/` 처럼 기능별로 나눈다 |
| **`_Project/` 로 우리 것과 남의 것을 가른다** | 에셋스토어 패키지는 자기 마음대로 `Assets/` 밑에 폴더를 만든다. 섞이면 "우리 코드가 어디까지인가"를 AI가 못 가린다 |
| **Unity 프로젝트는 `Unity/` 폴더 안에** | 이 저장소에는 Unity 가 아닌 툴(그림·사운드·MCP)도 들어올 예정이다. 뿌리를 Unity 가 차지하면 섞인다 |

> **왜 코드만 기능별인가** — 로컬 Qwen 에게 일을 시킬 때 "적 이동 속도 고쳐라"는 지시가 **폴더 하나로 정확히 떨어져야** 한다. `Scripts/Gameplay/Enemy/` 라고 말하면 끝이다. 반대로 유형별(`Scripts/Controllers/`, `Scripts/Managers/`)로 나누면 적 관련 코드가 세 폴더에 흩어져서 AI 가 전부 뒤져야 한다. 그림·소리는 AI 가 고칠 일이 없고 툴이 한곳에 쏟아붓는 쪽이라 유형별이 맞다.

### 2. asmdef — 처음엔 딱 2개, 기능별로 쪼개지 마라

| | 판정 |
| --- | --- |
| `Officina.Runtime` (Scripts/ 뿌리) | **만든다** |
| `Officina.Editor` (Scripts/Editor/) | **만든다** |
| `Officina.Tests` | 테스트를 쓰기로 하면 그때 |
| `Officina.Player`, `Officina.Enemy` 처럼 기능별 | **하지 마라** (지금은 손해) |

**로컬 LLM 지시에 asmdef 가 도움이 되나 → 반쯤만.** 이 프로젝트의 관심사라 따로 정리한다.

- **길 찾기에는 안 도움 된다.** AI 가 파일을 찾는 건 폴더 경로와 심볼 검색(Serena)이지 asmdef 가 아니다.
- **잘못 쓴 걸 잡아주는 데는 도움 된다.** asmdef 경계를 넘으면 **컴파일 에러**가 난다. "UI 코드에서 적 체력을 직접 만지지 마라"를 사람이 지켜보는 대신 컴파일러가 잡는다. AI 는 말로 한 규칙은 잘 어기지만 컴파일 에러는 못 어긴다. `[추측]` — 이 프로젝트에서 검증한 건 아니다.
- **`.asmdef` 파일 자체가 AI 가 읽을 수 있는 의존성 명세다.** JSON 한 장에 "이 덩어리는 무엇을 참조할 수 있나"가 적혀 있어서, 프롬프트에 그대로 붙일 수 있다.
- **그런데도 지금 쪼개면 안 되는 이유** : 스크립트 하나만 고쳐도 Unity 는 **도메인 리로드**를 한다. 어셈블리를 잘게 쪼개도 도메인 리로드는 그대로 일어나고, 타입 수가 늘면 TypeCache 재생성에 **약 300ms** 가 더 붙는다. `[전언]` 코드가 몇십 개일 때는 이득이 손해보다 작다.
- **쪼갤 때** : 기능이 셋 이상으로 확실히 갈리고, 실제로 컴파일이 답답해지고, "이쪽에서 저쪽 부르지 마라"가 반복해서 깨질 때. 그 전엔 폴더로 충분하다.

### 3. 아키텍처 — 쓸 것과 안 쓸 것

**쓸 것 (2D 소규모에 값어치 있음)**

| 패턴 | 어디에 |
| --- | --- |
| **Observer (C# `event`)** | 체력 변화 → UI 갱신처럼 "알려주기" |
| **State machine** | 캐릭터 상태(대기/이동/공격), 게임 흐름(메뉴/플레이/정지) |
| **Object pooling** | 총알·이펙트처럼 많이 생겼다 사라지는 것 |
| **ScriptableObject = 데이터 통** | 적 능력치, 아이템 표. 코드 고치지 않고 수치만 바꿈 |
| **Bootstrap 한 곳에서 조립** | 씬 시작 시 스크립트 하나가 필요한 것들을 이어 붙임 |

**안 쓸 것 (지금은 과투자)**

| 안 쓸 것 | 이유 |
| --- | --- |
| **ScriptableObject 이벤트 아키텍처** (Ryan Hipple / unity-atoms) | ★ 아래에 따로 설명 |
| **DI 컨테이너** (VContainer, Zenject) | 클래스 몇십 개에 배선 프레임워크는 배보다 배꼽 |
| **ECS / DOTS** | 2D 탑다운 소규모에 필요 없다. 코드 모양이 완전히 달라져서 AI 가 참고할 예제도 적다 |
| **MVC / MVP 전면 적용** | 메뉴가 많은 UI 위주 게임에서 값어치가 난다 `[전언]`. UI 화면이 복잡해지면 그때 UI 에만 |
| **유닛 테스트 전면 도입** | 100만 장 판 Thronefall 도 유닛 테스트·코드 리뷰 없이 2명이 만들었다 `[확인]` |
| **Addressables** | 빌드 하나짜리 2D 게임에 에셋 스트리밍은 불필요 |
| **스타터킷 통째로 도입** | 남의 프레임워크 규칙을 AI 에게 또 가르쳐야 한다. 폴더 트리만 베낀다 |

**★ SO 이벤트 아키텍처를 빼는 이유 — 이게 이 프로젝트에서 제일 중요한 판단이다**

Ryan Hipple 의 Unite Austin 2017 발표는 Unity 채널에서 **가장 많이 본 Unite 영상**이고 `[전언]`, unity-atoms 같은 라이브러리를 낳았다. 그 방식의 핵심 값어치는 **"프로그래머가 아닌 기획자가 인스펙터에서 직접 연결을 갈아 끼울 수 있다"** 는 것이다.

그런데 **이 프로젝트에는 인스펙터를 만지는 사람이 없다.** 기획도 코딩도 AI 가 한다. 그리고

> **AI 는 인스펙터를 못 본다.**

프리팹의 인스펙터 연결은 `.prefab` YAML 안의 GUID 로만 남는다. 로컬 Qwen 에게 "왜 이 이벤트가 안 불리냐"를 물으면 **코드에는 답이 없다.** 이건 SO 아키텍처만의 문제가 아니라 이 프로젝트 전체의 규칙이 되어야 한다.

> **규칙 후보 : 설정과 연결은 되도록 코드에 둔다. 인스펙터에서만 알 수 있는 배선은 만들지 않는다.**
> ScriptableObject 는 **수치 데이터 통**으로만 쓰고(그건 텍스트로 읽힌다), **이벤트 배선 도구**로는 쓰지 않는다.

### 4. 버전 관리 — 지금 상태와 할 일

| 항목 | 지금 | 할 일 |
| --- | --- | --- |
| `.gitignore` | github/gitignore 공식 Unity 판이 뿌리에 있음 `[확인]` | Unity 프로젝트를 `Unity/` 에 만들면 **이 파일을 `Unity/.gitignore` 로 옮긴다.** `/[Ll]ibrary/` 같은 경로가 뿌리 기준이라 그냥 두면 안 걸린다 |
| `.gitattributes` | **없음** | 프로젝트 만들 때 같이 만든다 (아래) |
| `.meta` | — | **대상 파일과 항상 같이 커밋.** 빠지면 참조가 조용히 깨진다 `[전언]` |
| `Library/` | — | 절대 커밋 안 함. 실수로 넣었으면 `git rm -r --cached Library` `[전언]` |
| `ProjectSettings/`, `Packages/manifest.json`, `packages-lock.json` | — | **반드시 커밋.** 없으면 다른 PC 에서 다른 게임이 열린다 `[전언]` |
| Git LFS | 없음 | **지금 최소한만 걸어두고 시작한다** (이유 아래) |

**Git LFS — 지금 안 걸면 나중에 히스토리를 다시 써야 한다**

2D 픽셀아트 PNG 는 작아서 LFS 없이도 당분간 멀쩡하다. 그런데 LFS 는 **나중에 붙여도 이미 들어간 커밋은 안 옮겨진다.** 나중에 옮기려면 히스토리 재작성이라 미니PC 와 동기화가 깨진다. **비용이 0에 가까우니 처음에 걸어두는 게 싸다.**

프로젝트 만들 때 `Unity/.gitattributes` 에 넣을 최소본 (오디오와 큰 이미지만) :

```
*.wav  filter=lfs diff=lfs merge=lfs -text
*.ogg  filter=lfs diff=lfs merge=lfs -text
*.mp3  filter=lfs diff=lfs merge=lfs -text
*.psd  filter=lfs diff=lfs merge=lfs -text
*.aseprite filter=lfs diff=lfs merge=lfs -text
```

> 픽셀 스프라이트 `*.png` 는 **일부러 뺐다.** 작고, LFS 에 넣으면 diff 로 확인이 안 되고, 사운드 툴·그림 툴이 대량으로 뱉을 때 LFS 대역폭만 먹는다. 나중에 큰 아틀라스가 생기면 그때 추가.

**Unity + Git 에서 흔히 터지는 것**

1. **`.meta` 누락** — 제일 흔하고 제일 조용히 망가진다. 파일만 커밋하고 `.meta` 를 빼면 다른 환경에서 GUID 가 새로 생겨 연결이 전부 끊긴다.
2. **씬·프리팹 병합 충돌** — `.unity`, `.prefab` 은 YAML 이라 텍스트 병합이 되긴 하는데 사람이 풀 수 있는 모양이 아니다. Unity 가 같이 주는 **UnityYAMLMerge** 를 git mergetool 로 붙일 수 있다. 1인이라 자주는 안 나지만 브랜치를 쓰면 난다. `[전언]`
3. **Windows 경로 260자 제한** — 폴더를 너무 깊이 파면 Unity 가 아니라 git 이 먼저 터진다. `git config core.longpaths true` 로 완화. 위 권장 트리를 더 깊게 파지 않는 이유이기도 하다.
4. **대소문자** — Windows 는 `Player.cs` 와 `player.cs` 를 같은 파일로 본다. 이름 바꾸기 커밋이 반영이 안 되는 사고가 난다. `git mv` 를 쓴다.
5. **저장소 크기** — GitHub LFS 는 20~30GB 부터 실제로 아프다 `[전언]`. 2D 프로젝트는 걱정할 규모가 아니다.

### C. asmdef

- **Unity 공식 매뉴얼** `[확인]` — 패키지 기준으로 **코드가 있는 폴더당 asmdef 하나**로 시작하고, 필요할 때만 더 만들라고 한다. 기본 네 폴더는 `Editor`, `Runtime`, `Tests/Editor`, `Tests/Runtime`. **Editor → Runtime 참조는 되지만 반대는 안 된다**(단방향). asmdef 는 손으로 고치지 말고 에디터에서 편집하라고 경고한다.
- **컴파일 시간** `[전언]` — asmdef 의 1차 목적은 컴파일 시간 단축이다. 그런데 실무 경험담 : *"공용/일반 asmdef 에 있는 코드라 다른 asmdef 들이 전부 참조하면, 컴파일 시간은 똑같거나 오히려 느리다. 특정 코드만 바뀔 때만 빨라진다."*
- **도메인 리로드가 진짜 병목** `[전언]` — Unity 는 스크립트 하나만 바뀌어도 **단일 스크립트만 다시 못 읽는다.** 컴파일 뒤 도메인 리로드가 일어나 C# 상태가 전부 날아간다. 타입이 많으면 **TypeCache 재생성만 약 300ms**. **어셈블리를 많이 쪼갤수록 이 부분은 나빠질 수 있다.**
- **아키텍처 효과** `[전언]` — asmdef 에 들어간 스크립트를 쓰려면 **asmdef 통째로 참조해야 한다.** 그래서 의존성을 만들 때 "정말 이걸 참조해야 하나"를 한 번 생각하게 된다. Unity 포럼 실사용자 표현 : *"오디오 스크립트가 갑자기 플레이어 체력에 손을 뻗는 걸 막는 단방향 의존성을 강제한다."*
- **안 쓰는 쪽 근거** `[전언]` — 같은 포럼 : *"asmdef 로 풀려는 문제가 뭔가? 없다면 복잡도만 늘리는 거니 다시 생각해 보라."* 또 기능 경계가 불분명한 상태로 만들면 컴파일 에러만 난다.

### D. 아키텍처 자료

- **Unity 공식 e-book** `[전언]` — *"Level up your code with game programming patterns"* (100쪽, 무료). 개정판 **"Level up your code with design patterns and SOLID"** 는 **Unity 6 기준**. Factory·Singleton·Command·State·Observer 와 SOLID 를 다룬다.
  - 예제 저장소 : `Unity-Technologies/game-programming-patterns-demo` (별 1.7k) `[확인]`. Observer, State, Object pooling, **MVC·MVP**, Factory, Command 예제가 들어 있다.
  - **저장소 라이선스를 확인하지 못했다.** 쓰기 전에 봐야 한다.
  - 저장소 스스로 *"권장안이 아니라 출발점"* 이라고 밝힌다. 그대로 베끼는 물건이 아니다.
- **ScriptableObject 아키텍처** `[전언]` — Ryan Hipple, Unite Austin 2017. Unity 유튜브 채널 **최다 조회 Unite 영상**. 예제 : `roboryantron/Unite2017`. 파생 라이브러리 `unity-atoms`. 배경은 "Manager·Controller·ControllerManager 같은 싱글턴 만능칼 클래스"에 대한 반발이었고, 목표는 **"기술자가 아닌 스태프도 조각을 다시 조립할 수 있게"** 하는 것이었다. 더 가벼운 파생판(`GenericScriptableArchitecture`)이 나온 것 자체가, 원본이 소규모엔 과하다는 평가가 있었다는 뜻이다.
- **MVC/MVP** `[전언]` — 규모가 어느 정도 커지기 전엔 이점이 안 보인다. **메뉴가 많고 로직 위주인 프로젝트**에 잘 맞는다. 장점은 로직과 UI 분리라 **플레이 모드에 안 들어가고도 검증**할 수 있다는 것.

3. **Unity 버전과 렌더 파이프라인** — 2D 라면 **Unity 6 LTS + URP 2D** 가 무난하다. 정해지면 스튜디오 저장소의 개발환경 문서를 고친다.
4. **`.gitattributes` 를 지금 만들어 둘까?** 위에 최소본을 적어뒀다. **나중에 붙이면 히스토리를 다시 써야 해서** 지금이 싸다.
5. **"인스펙터에 배선을 숨기지 않는다" 를 `AGENTS.md` 규칙으로 올릴까?** 이번 조사에서 나온 제일 중요한 판단인데, 규칙으로 못 박으면 AI 가 프리팹에 이벤트를 꽂아두는 걸 미리 막을 수 있다.
6. **다음 단계는 설계인가, 바로 프로젝트 생성인가?** 규칙상 조사 → 설계 → 작업이라, 다음은 `Docs/Design/2026-08-20-Unity프로젝트구조설계.md` 를 쓰는 순서다. 건너뛰라면 그렇게 한다.
