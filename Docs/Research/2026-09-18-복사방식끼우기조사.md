# 복사 방식으로 끼우기 — 자리·꼴·치환·스크립트 조사

조사일 : 2026-09-18
전제 : **끼우는 법은 「복사」로 확정됐다** (사용자 확정 2026-09-18 · mem `20260918-64c13c96`).
CodeTool 안의 템플릿을 게임 프로젝트에 통째로 복사하고 네임스페이스만 게임 이름으로 치환한다. UPM 로컬 패키지 참조는 안 쓴다.
대상 : 대상 게임 프로젝트는 Unity **6000.3.23f1** · 2D URP · `com.unity.ide.visualstudio 2.0.26` · `com.unity.ide.rider 3.0.40`.
표기 : `[확인]` 1차 자료(파일·소스 코드)를 직접 봄 · `[전언]` 검색 요약이나 2차 자료만 봄 · `[추측]` 근거 있는 내 판단
안 한 것 : Unity 를 실행하지 않았다. 게임 프로젝트는 **읽기만** 했다.

## 1. 설정 파일 자리와 효력

### 1-1. `.globalconfig` 는 `Assets/` 안이어야 한다

- **전체에 걸려면** `Assets/Default.globalconfig`, **어셈블리 하나에만** 걸려면 그 `.asmdef` 와 같은 폴더에 둔다. 파일 맨 위에 `is_global = true` 를 쓰고 `dotnet_diagnostic.<ID>.severity = error` 를 적는다. `[전언]`
- **Unity 2021.3 부터 동작하고 Unity 6 매뉴얼에서 정식 문서화됐다.** `[전언]`
- **Unity 프로젝트 루트(Assets 밖)에 두면 효력이 없다.** 근거 둘 :
  1. Unity 는 애널라이저 설정을 `ScriptCompilerOptions.AnalyzerConfigPath` 로 넘기는데, 이 값은 **에셋 파이프라인이 훑는 범위(`Assets/`·패키지) 안의 파일**에서 온다. `[전언]`
  2. Unity 가 만드는 csproj 는 **SDK 형식이 아니다.** 실제 파일 머리가 `<Project ToolsVersion="4.0" … xmlns=…/developer/msbuild/2003>` 이고 마지막에 `Microsoft.CSharp.targets` 를 직접 `Import` 한다 `[확인]`. 그래서 .NET SDK 가 프로젝트 폴더의 `.globalconfig` 를 알아서 집어넣는 동작(있다 해도)이 걸리지 않는다. `[추측]`
- **`.editorconfig` 는 Unity 에디터 컴파일에서 여전히 무시된다** (Unity 이슈 Won't Fix). 이건 옛 조사(`2026-08-20-코드컨벤션조사.md` 3-1절)에서 확인된 그대로다.

### 1-2. csproj 에 들어가는 방식 — IDE 패키지 소스를 직접 읽었다

두 IDE 패키지 모두 `ScriptCompilerOptions.AnalyzerConfigPath` 를 읽어 csproj 에 쓴다. **쓰는 항목 이름이 다르다.**

| 패키지 | 버전 | csproj 에 쓰는 것 | 근거 (패키지 소스) |
| --- | --- | --- | --- |
| `com.unity.ide.rider` | 3.0.40 | `<GlobalAnalyzerConfigFiles Include="…" />` | `Rider/Editor/ProjectGeneration/ProjectGeneration.cs:766~787` `[확인]` |
| `com.unity.ide.visualstudio` | 2.0.26 | `<EditorConfigFiles Include="…" />` | `Editor/ProjectGeneration/ProjectGeneration.cs:793~796` `[확인]` |

둘 다 같이 넣는 것 : `<Analyzer Include=…>`(애널라이저 DLL) · `<CodeAnalysisRuleSet>`(`.ruleset`) · `<AdditionalFiles Include=…>`(`.additionalfile`).

**함정 두 개** `[확인]`

1. **VS 패키지의 애널라이저 블록은 조건부다.** `SetAnalyzerAndSourceGeneratorProperties` 첫 줄이
   `if (m_CurrentInstallation == null || !m_CurrentInstallation.SupportsAnalyzers) return;` 다.
   즉 **Visual Studio 설치가 감지되지 않으면 애널라이저·`.globalconfig` 항목이 csproj 에 아예 안 들어간다.**
   Unity 안 컴파일에는 영향이 없지만, **IDE·`dotnet` 쪽 검사만 조용히 빠진다.**
2. **VS 패키지는 `EditorConfigFiles` 라는 이름으로 넣는다.** `.globalconfig` 파일을 `EditorConfigFiles` 항목에 넣어도 컴파일러에는 `/analyzerconfig:` 로 넘어가고 `is_global = true` 는 파일 내용으로 판별되므로 동작할 것으로 본다 — **다만 실제로 먹는지는 확인하지 못했다.** `[추측]`

### 1-3. 지금 게임 프로젝트에서 실제로 보이는 것

`.globalconfig` 가 없는 상태의 생성된 csproj(`Assembly-CSharp-Editor.csproj`)를 읽었다. `[확인]`

- `<EditorConfigFiles>` · `<GlobalAnalyzerConfigFiles>` · `<CodeAnalysisRuleSet>` **항목이 하나도 없다.** 파일이 없으니 당연하다 — 반대로 **파일을 넣으면 여기 줄이 생기는지가 설계 뒤 첫 검증 항목이다.**
- **`Microsoft.Unity.Analyzers.dll` 은 이미 들어 있다.** Visual Studio Tools for Unity 설치 폴더에서 `<Analyzer Include=…>` 로 자동 주입된다. 옛 조사의 「설치 없이 이미 돌고 있을 가능성이 높다」가 이 프로젝트에서 사실로 확인됐다.
- Unity 엔진이 넣는 소스 제너레이터 3개(`Unity.SourceGenerators` · `Unity.Properties.SourceGenerator` · `Unity.UIToolkit.SourceGenerator`)도 같이 들어 있다.
- 실제 컴파일 명령(`Library/Bee/artifacts/…/*.rsp`)에는 `-analyzer:` 와 `/additionalfile:` 이 들어 있고 `-langversion:9.0` 이다. `-analyzerconfig:` 는 (파일이 없어서) 없다.

### 1-4. 애널라이저 DLL 을 `Assets/` 에 넣는 방식과 asmdef 범위

- 넣는 법 : DLL 을 `Assets/` 아래 두고 **Plugin Inspector 에서 플랫폼을 전부 끄고 `RoslynAnalyzer` 라벨**을 붙인다. `[전언]`
- **범위** : 애널라이저가 **asmdef 가 있는 폴더(또는 그 하위)에 있으면 그 어셈블리에만** 걸린다. `Assets/` 루트에 두면 전부에 걸린다. Unity 6.3 매뉴얼 원문 : *"If an analyzer is in a folder that contains an assembly definition file, or one of its subfolders, the analyzer only applies to that assembly."* `[확인]`
- **복사 방식에서의 함의** : asmdef 가 Runtime/Editor 둘뿐이므로 **DLL 은 `Assets/` 루트에 한 벌 두는 것이 가장 단순하다.** asmdef 옆에 두면 어셈블리마다 DLL 사본이 필요해진다. `[추측]`
- **git 함정** : 게임 저장소 `.gitattributes` 가 `*.dll` 을 LFS 로 잡고 있다 `[확인]`. 애널라이저 DLL 을 커밋하면 LFS 대역폭을 쓴다. 라벨·플랫폼 설정은 `.meta` 안에 있으므로 **DLL 과 `.meta` 를 반드시 같이** 넣어야 한다.
- **BannedApiAnalyzers 의 알려진 위험** : Unity 는 애널라이저 설정 파일을 **`파일이름.[애널라이저이름].additionalfile`** 이라는 이름 규칙으로만 넘긴다. BannedApiAnalyzers 는 `BannedSymbols.txt` 라는 고정 이름을 기대해서 **이름이 안 맞을 수 있다.** `[전언]` — Unity 가 `/additionalfile:` 을 실제로 넘긴다는 것까지는 확인했지만, 이 애널라이저가 Unity 안에서 금지 목록을 읽는지는 **확인 못 했다.**

### 1-5. CSharpier 설정 자리와 Unity 프로젝트에서 돌리는 법

- 설정 파일 : **`.csharpierrc`(JSON·YAML) · `.csharpierrc.json` · `.csharpierrc.yaml` · `.editorconfig`** `[확인]`
- 찾는 방식 : **고치는 파일에서 위로 올라가며** 찾는다. 같은 폴더면 `.csharpierrc*` 가 `.editorconfig` 를 이긴다. `[확인]`
- 옵션 : `printWidth`(기본 100) · `useTabs` · `indentSize` · `endOfLine` · `xmlWhitespaceSensitivity`. **그뿐이다.**
- **Unity 와의 궁합이 좋은 이유** : `dotnet csharpier format <폴더>` 는 csproj·솔루션이 필요 없다. Unity 가 csproj 를 계속 다시 만드는 것과 **무관하게** 돈다. 대상 폴더를 `Assets/<코드루트>` 로 좁히면 `Library/`·패키지 캐시를 훑을 일도 없다. `[추측]`
- 자리 후보 : **저장소 뿌리**(툴 설정을 한 곳에 모음) 또는 **Unity 프로젝트 루트**(Unity 프로젝트만 떼어 가도 따라감). 위로 올라가며 찾으므로 둘 다 동작한다.
- **설계에서 풀어야 할 불일치** : `Docs/Todo/코드와저장소.md` 는 자동 고침을 **CSharpier** 로 적었는데, 그 뒤 조사(`2026-08-20-CSharp포매터대안조사.md`)는 **`dotnet format` + `.editorconfig`** 를 권했다. 둘은 「옵션이 없어 논쟁이 없다」 대 「취향을 반영할 수 있다」의 맞바꿈이고 **아직 한쪽으로 안 정해졌다.**

### 1-6. 정리 — 설정 파일은 두 겹이다

```
저장소 뿌리 또는 Unity 프로젝트 루트
  .csharpierrc  (또는 .editorconfig)   → Unity 밖 검사 (CSharpier / dotnet format / IDE)
Assets/
  Default.globalconfig                 → Unity 안 컴파일 심각도 (is_global = true)
  <애널라이저>.dll + .meta              → RoslynAnalyzer 라벨 · 플랫폼 전부 끔
```

## 2. 템플릿 폴더 꼴

### 2-1. 한 폴더로 못 묶는다 — 목적지가 세 군데다

게임 프로젝트의 실제 배치 `[확인]` : **저장소 뿌리 ≠ Unity 프로젝트 루트다.** Unity 프로젝트는 저장소 안의 하위 폴더 하나이고, `.gitignore`·`.gitattributes` 는 **저장소 뿌리**에 있으면서 Unity 경로 앞에 프로젝트 폴더 이름을 접두사로 붙여 쓴다.

| 복사 원본 | 가는 자리 | 안에 들어갈 것 |
| --- | --- | --- |
| `Template/RepoRoot/` | 저장소 뿌리 | `.gitignore` · `.gitattributes` |
| `Template/UnityRoot/` | Unity 프로젝트 루트 | `.csharpierrc`(또는 `.editorconfig`) · (쓰기로 하면) 서식용 가짜 csproj |
| `Template/Assets/` | `Assets/` | `Default.globalconfig` · 애널라이저 DLL · 코드 루트 폴더 트리 · asmdef 2개 · 뼈대 `.cs` |

**폴더 이름 후보** : `Template/`(단수, 후보) · `Templates/` · `Kit/` · `Scaffold/`.
`Template/` 밑을 위 표처럼 **목적지 이름으로 가르는 것**이 「어디에 복사하나」를 문서 없이 알 수 있게 한다. `[추측]`

### 2-2. 폴더 트리 표준안 (Unity 6 · 2D URP)

옛 조사(`2026-08-20-Unity프로젝트구조조사.md`)의 트리를 그대로 쓰고, 실제 프로젝트 상태만 반영했다.

```
<저장소 뿌리>/
├─ .gitignore                     ← Unity 경로에 프로젝트 폴더 접두사가 붙어 있다
├─ .gitattributes
└─ <Unity 프로젝트>/
   ├─ .csharpierrc
   ├─ Assets/
   │  ├─ Default.globalconfig     ← 전체 심각도
   │  ├─ Scenes/                  ← Unity 가 만든 것 (그대로)
   │  ├─ Settings/                ← URP 2D 설정 (Unity 가 만든 것)
   │  └─ _Project/                ← ★ 템플릿이 만드는 우리 것
   │     ├─ Art/{Sprites,Tiles,UI}/
   │     ├─ Audio/{BGM,SFX}/
   │     ├─ Data/  Prefabs/  Scenes/
   │     └─ Scripts/
   │        ├─ <이름>.Runtime.asmdef
   │        ├─ Core/  Gameplay/{Player,Enemy,World}/  UI/
   │        └─ Editor/
   │           └─ <이름>.Editor.asmdef
   ├─ Packages/  ProjectSettings/  (Unity 가 관리 · 반드시 커밋)
   └─ Library/  Temp/  Logs/  UserSettings/  (커밋 안 함)
```

- **`Assets/Settings/` 는 URP 프로젝트를 만들면 Unity 가 이미 만들어 둔다** `[확인]` — 템플릿이 만들 필요가 없다. 겹치면 오히려 위험하다.
- 폴더를 **4단계 넘게 파지 않는다** (Windows 경로 길이). 옛 조사 결론 그대로.

### 2-3. `.gitignore` — 접두사 문제가 복사 방식의 진짜 걸림돌이다

`github/gitignore` 의 Unity 판은 **Unity 프로젝트가 저장소 뿌리에 있다고 보고** `/[Ll]ibrary/` 처럼 경로를 적는다 `[전언]`. Unity 프로젝트를 하위 폴더에 두면 이 경로가 안 맞아서, 지금 게임 저장소는 **모든 줄에 프로젝트 폴더 이름을 손으로 붙여 놓았다** `[확인]`.

| 안 | 내용 | 값 |
| --- | --- | --- |
| **가. 뿌리에 한 장 + 접두사 치환** | 템플릿의 `.gitignore` 에 접두사 자리표시자를 두고 복사 때 Unity 폴더 이름으로 바꾼다 | 지금 게임 저장소와 같은 모양이 된다. 대신 **치환 대상이 네임스페이스 말고 하나 더 늘어난다** |
| **나. Unity 폴더 안에 `.gitignore`** | 접두사 없이 공식 Unity 판을 그대로 둔다 | 치환이 없다. 대신 **지금 게임 저장소의 뿌리 `.gitignore` 와 규칙이 겹친다** — 어느 쪽이 이기는지 사람이 헷갈린다 |
| **다. Unity 프로젝트를 저장소 뿌리에 두기** | 공식 판을 그대로 쓴다 | **이 프로젝트에는 해당 없다.** 실제 배치가 하위 폴더다 |

### 2-4. `.gitattributes` — LFS 범위가 두 판단으로 갈려 있다

`* text=auto eol=lf` 로 줄 끝을 통일하고, 큰 이진 파일을 LFS 로 잡는 것이 표준이다. **범위가 문서마다 다르다.**

| | 옛 조사(`2026-08-20`) | 실제 게임 저장소 `[확인]` |
| --- | --- | --- |
| 소리·편집 원본(`wav` `ogg` `psd` `aseprite`) | LFS | LFS |
| **`*.png` 등 그림** | **일부러 뺐다** (작고 diff 가 보이는 게 낫다) | **LFS 에 넣었다** |
| `*.dll` · `*.zip` · 글꼴 | 언급 없음 | LFS |

- **LFS 는 나중에 붙여도 이미 들어간 커밋은 안 옮겨진다.** 히스토리 재작성이 필요하므로 **템플릿이 처음에 넣어 주는 값이 크다.** 옛 조사 결론 그대로.
- 템플릿이 게임 저장소보다 **좁은** 판을 들고 있으면, 복사할 때 기존 `.gitattributes` 를 덮어 **이미 LFS 로 들어간 `*.png` 가 규칙만 풀리는** 사고가 난다. `[추측]` → 4장의 덮어쓰기 규칙과 직결된다.

## 3. 네임스페이스 치환 방식

### 3-1. 두 안 비교

| | 가. 실제 이름 `Officina.*` 를 그대로 두고 치환 | 나. `__NAMESPACE__` 자리표시자 |
| --- | --- | --- |
| CodeTool 안에서 문법·서식 검사 | **된다** | **된다.** `__NAMESPACE__` 는 **유효한 C# 식별자**라 파싱·CSharpier 검사가 깨지지 않는다 `[추측]` (밑줄 두 개는 예약어가 아니다) |
| CodeTool 안에서 **실제 컴파일** | 어차피 **못 한다.** 저장소에 Unity 가 없어 `UnityEngine` 을 참조할 수 없다 | 같다 |
| 사람이 읽기 | 그냥 코드처럼 읽힌다 | 눈에 거슬리고 예제로 붙여쓰기 어렵다 |
| **치환 오탐** | **위험하다.** `Officina` 는 툴킷 이름이라 라이선스 머리글·주석·문서에도 나올 수 있다. 통째 문자열 치환이 엉뚱한 곳을 바꾼다 | **오탐 0.** 자리표시자는 바꿀 자리에만 있다 |
| 덜 치환 위험(빠뜨림) | 남은 `Officina.` 가 **컴파일은 되고** 이름만 어긋난다 → 조용히 지나간다 | 남은 `__NAMESPACE__` 도 **컴파일은 된다** → 역시 조용하다. 다만 검색이 쉽다 |

**절충안** `[추측]` : 실제 이름을 두되 **치환 대상을 정규식 `\bOfficina\.` 로 한정**하고, 라이선스·주석의 「Officina」(점이 안 붙은 것)는 안 건드린다. 복사 뒤 **남은 `Officina.` 개수가 0인지 세는 검사**를 스크립트가 같이 한다.

### 3-2. 같이 치환해야 하는 것

| 대상 | 왜 | 확인 |
| --- | --- | --- |
| `.cs` 안의 `namespace …` 와 `using …` | 본체 | — |
| **asmdef 의 `name`** | 어셈블리 이름이고 다른 asmdef 가 이 이름으로 참조한다 | 매뉴얼 원문 : *"Name: The name of the assembly. Other scripts can reference this name in their own `.asmdef` files."* `[확인]` |
| **asmdef 파일 이름** (`Officina.Runtime.asmdef`) | 관행상 `name` 과 같게 쓴다. **파일 이름까지 바꿀지가 결정거리** | — |
| **asmdef 의 `rootNamespace`** | Unity 가 새 스크립트를 만들 때 쓰고 csproj `<RootNamespace>` 로 나간다 | 필드 존재는 `[전언]` — **Unity 6.3 asmdef 매뉴얼에는 설명이 없다** `[확인-없음]` |
| `PrefabKeys` 같은 코드 상수 | 네임스페이스가 안 들어가면 치환 대상이 아니다 | — |

지금 게임 프로젝트는 `ProjectSettings/EditorSettings.asset` 의 `m_ProjectGenerationRootNamespace` 가 **비어 있고** 생성된 csproj 의 `<RootNamespace>` 도 **비어 있다** `[확인]`. 즉 **아무도 네임스페이스를 강제하고 있지 않다** — 뼈대가 쓰는 네임스페이스가 그대로 사실이 된다.

### 3-3. C# 버전 — 뼈대 문법에 바로 걸린다

`-langversion:9.0` `[확인, `.rsp` 와 csproj 둘 다]`. Unity 6000.3 이 **C# 9** 다.

- **쓸 수 있는 것** : `record` · `init` · 대상 타입 `new()` · 패턴 매칭 개선
- **쓸 수 없는 것** : **file-scoped namespace(`namespace Foo;`)** · `global using` · `required` 멤버 (모두 C# 10 이상)
- **함의** : 뼈대는 **중괄호 네임스페이스**로 써야 한다. 치환 대상 줄 모양도 `namespace Officina.Xxx` **한 줄**로 고정된다 — 정규식 치환이 쉬워진다. `[추측]`

### 3-4. `.meta` 함정

Unity 는 에셋마다 `.meta` 에 **GUID** 를 적어 두고, 이 GUID 로 프리팹·씬이 스크립트를 가리킨다.

- 템플릿에 `.meta` 를 **넣으면** 같은 GUID 가 여러 게임 프로젝트에 퍼진다. 한 프로젝트 안에서는 안 겹치니 당장 문제는 없지만, 프로젝트 둘을 합칠 때 충돌한다. `[추측]`
- 템플릿에 `.meta` 를 **안 넣으면** Unity 가 처음 열 때 새로 만들어 준다. **다시 복사(갱신)할 때 `.meta` 를 덮어쓰지 않는 것이 중요하다** — 덮으면 GUID 가 바뀌어 프리팹 참조가 조용히 끊긴다. 애널라이저 DLL 만 예외다(라벨·플랫폼 설정이 `.meta` 안에 있어 같이 가야 한다).

## 6. 확인 못 한 것

- **`.globalconfig` 를 넣으면 실제로 csproj 에 줄이 생기고 Unity 안에서 심각도가 먹는지.** Unity 를 안 돌렸다. 패키지 소스로 「그렇게 쓰게 돼 있다」까지만 봤다.
- **VS 패키지가 `EditorConfigFiles` 로 넣은 `.globalconfig` 가 IDE·`dotnet` 쪽에서 실제로 먹는지.** 항목 이름이 `GlobalAnalyzerConfigFiles` 가 아니라서 남은 의문이다.
- **VS 설치가 감지되지 않는 환경**(Rider 만 쓰는 경우 등)에서 csproj 가 어떻게 나오는지.
- **BannedApiAnalyzers 가 Unity 안에서 금지 목록을 읽는지.** `.additionalfile` 이름 규칙과 안 맞을 수 있다는 지적만 봤다 — 옛 조사에서도 못 확인했다.
- **asmdef 의 `rootNamespace` 필드** — Unity 6.3 asmdef 매뉴얼 페이지에 설명이 없었다. 필드 존재와 동작은 2차 자료뿐이다.
- **`.ruleset` 과 `.globalconfig` 를 같이 뒀을 때 어느 쪽이 이기는지.** 옛 조사에서도 못 확인했고 이번에도 못 했다.
- **`__NAMESPACE__` 가 CSharpier·Roslyn 파싱을 실제로 통과하는지.** C# 식별자 규칙상 된다고 봤지만 돌려보지는 않았다.
- **Unity 엔진 쪽 어셈블리에서 `.globalconfig` 파일을 찾는 규칙**(파일 이름·검색 순서)을 1차 자료로 못 봤다. 엔진 DLL 문자열 검색은 실패했다(대조군인 `Default.ruleset` 도 안 잡혀 방법 자체가 못 미쳤다).
- **CSharpier `.csharpierignore`** — 공식 설정 문서에 항목이 없었다. 옛 조사에 있던 내용이라 버전이 바뀌었을 수 있다.
