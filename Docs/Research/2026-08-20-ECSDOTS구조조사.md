# ECS/DOTS 구조 조사

## 결정 (2026-08-20) : ECS 보류

**기본 구조(`Docs/Todo/기본구조.md`)를 그대로 쓴다. ECS/DOTS 는 도입하지 않는다.**

이유 : 우리 기본값이 2D 스프라이트인데, `SpriteRenderer` 는 Entities Graphics 에서 컴패니언 컴포넌트라
**결국 GameObject 로 남는다.** 스프라이트를 엔티티로 그리려면 NSprites 나 쿼드 직접 그리기로 가야 하고,
그러면 URP 2D 기능을 포기하게 된다. 계산 쪽 이득만 얻자고 치르기엔 비용이 크다.

나중에 다시 볼 조건 : 화면에 도는 것이 수천 단위로 늘어나거나, 2D 렌더 문제가 풀렸을 때.
그때는 아래 **안 A(하이브리드)** 부터 본다.

아래는 그때 다시 읽을 조사 내용이다.

---

## 결론 먼저

1. **`Docs/Todo/기본구조.md` 구조를 ECS 에 그대로 쓸 수 없다.** 이름만 바꿔 다는 수준으로는 안 되고, 4개 층 중 아래 두 층(`~Object`, `~Agent`)은 통째로 사라진다.
2. **그렇다고 버릴 문서도 아니다.** 위 두 층(`~Master`, `~Manager`/`~Hub`)은 **ECS 월드 바깥의 관리층**으로 살아남는다. 아웃게임·UI·저장·씬 전환은 여전히 이 구조가 맞다.
3. **다만 우리 프로젝트 기본값(2D 탑다운 스프라이트)에서 DOTS 는 지금 지뢰밭이다.** Entities Graphics 가 **URP 2D Renderer / SpriteRenderer 를 지원하지 않는다.** 스프라이트를 엔티티로 그리려면 서드파티(NSprites) 를 쓰거나 직접 만들어야 한다. 이게 이번 조사에서 나온 제일 큰 위험이다.

---

## 1. 기존 구조를 그대로 쓰면 안 되는 이유

### 1-1. 방향이 90도 다르다

MonoBehaviour 구조는 **세로**다. 오브젝트 하나를 잡고 그 안의 함수를 부른다.
ECS 는 **가로**다. 시스템 하나가 "이 컴포넌트를 가진 모든 엔티티"를 한 번에 훑는다.

```
[기존]  Player.Update() → Move() → View.Update()      (오브젝트별로 세로 관통)
[ECS]   MoveSystem     : 움직이는 모든 것의 위치를 한 번에
        AnimSystem     : 그림 가진 모든 것의 프레임을 한 번에   (기능별로 가로 관통)
```

`~Object` 는 "데이터와 기능을 한 덩어리로 묶은 것"인데, ECS 는 그 덩어리를 깨서 **데이터(IComponentData)와 기능(System)을 따로 두는 것**이 존재 이유다. 덩어리를 유지하면 ECS 를 쓰는 의미가 없다.

### 1-2. `~Master` 가 하던 일을 Unity 가 이미 한다

`~Master` 의 핵심은 "Manager 들을 new 하고 Init / Process / LateProcess 를 순서대로 불러준다" 였다. ECS 에서는 이걸 **월드(World)와 시스템 그룹**이 대신한다.

| `IManager` | ECS 대응 |
| --- | --- |
| `Init` | `ISystem.OnCreate` |
| `Process(deltaTime)` | `SimulationSystemGroup` 안의 `OnUpdate` |
| `FixedProcess(deltaTime)` | `FixedStepSimulationSystemGroup` 안의 `OnUpdate` |
| `LateProcess(deltaTime)` | `PresentationSystemGroup` 안의 `OnUpdate` |
| `Dispose` | `ISystem.OnDestroy` |
| Master 가 부르는 순서 | `[UpdateInGroup]` / `[UpdateBefore]` / `[UpdateAfter]` 특성 |

시스템은 기본적으로 **자동 생성**된다. 손으로 관리하고 싶으면 `[DisableAutoCreation]` + `ICustomBootstrap` 을 쓴다. 즉 `~Master` 는 없애거나, 있어도 **부트스트랩 한 장**으로 얇아진다.

루트 그룹은 3개다.
- `InitializationSystemGroup` — 플레이어 루프 Initialization 끝
- `SimulationSystemGroup` — Update 끝
- `PresentationSystemGroup` — PreLateUpdate 끝

### 1-3. `~Hub` 의 static 캐싱이 Burst 를 막는다

`~Hub` 는 싱글턴을 줄이려는 좋은 의도지만, **static 클래스가 managed 인터페이스(`I~Hub`)를 들고 있는 형태**다. 이건 잡(Job)이나 Burst 컴파일된 코드에서 **접근할 수 없다.** DOTS 를 쓰는 이유의 절반이 Burst + Job 인데, Hub 를 통해 참조하는 코드는 그 절반을 포기하게 된다.

ECS 에서 "전역 하나짜리 값"은 **싱글턴 컴포넌트**로 푼다. 엔티티 하나에만 붙은 컴포넌트를 `SystemAPI.GetSingleton<T>()` 로 꺼낸다. 다른 엔티티 값을 봐야 하면 `ComponentLookup<T>` 를 쓴다. 둘 다 잡 안에서 안전하게 쓸 수 있다.

## 2. 층별 대응표

| 기존 층 | MonoBehaviour 세계 | ECS 세계 | 살아남나 |
| --- | --- | --- | --- |
| `~Master` | GameObject 1개가 Manager new + 생명주기 호출 | `World` + `ICustomBootstrap` (거의 Unity 가 함) | **거의 사라짐** |
| `~Manager` | `IManager` 구현 클래스 | `ISystem` (구조체, Burst 가능) / `SystemBase` (클래스, managed 필요할 때) | **개념만 남음** |
| `~Hub` / `I~Hub` | static 캐싱, 인터페이스 노출 | 싱글턴 컴포넌트, `ComponentLookup` | **형태가 바뀜** |
| `~Object` | 클래스 + State | `Entity` + `IComponentData` 조합. 상속 없음, State 는 태그 컴포넌트나 enum 필드 | **사라짐** |
| `~Agent` | 책임 무거워지면 하위 클래스로 분리 | 시스템을 쪼갠다. `ViewAgent` → 렌더 컴포넌트 + Presentation 그룹 시스템 | **사라짐 (시스템 분리로 대체)** |
| `~Handler` | 반복 기능 모은 헬퍼 | Burst 가능한 `static` 유틸 함수, `IJobEntity` | **거의 그대로 살아남음** |

`~Handler` 가 멀쩡한 이유는 원래부터 상태 없는 순수 기능 묶음이기 때문이다. 데이터 지향과 충돌하지 않는다.

### ECS 쪽 추가 개념 (기존 문서에 없는 것)

- **Authoring + Baker** — 에디터에서 만든 GameObject 를 엔티티로 굽는다. 클래스 이름 뒤에 `Authoring` 을 붙이는 게 관례다.
- **SubScene** — 구워진 엔티티가 담기는 씬. ECS 콘텐츠는 여기 들어간다.
- **EntityCommandBuffer** — 잡 안에서는 엔티티 생성/삭제를 바로 못 한다. 명령을 모아뒀다 나중에 실행한다. `~Manager` 가 하던 "Object 생성·제거" 가 여기로 간다.
- **BlobAsset** — 읽기 전용 데이터 덩어리. ScriptableObject 수치 데이터통의 ECS 판이다.

## 3. 제일 큰 문제 : 2D 스프라이트가 안 그려진다

우리 기본값은 **2D 탑다운 + URP 2D + 64×64 스프라이트**다. 그런데:

- **Entities Graphics 는 URP 의 Forward+ 만 지원하고 2D Renderer 는 지원하지 않는다.**
- **`SpriteRenderer` 는 컴패니언 컴포넌트(companion component)로만 처리된다.** 서브씬에 넣고 시스템에서 조회는 되지만 **실체는 여전히 GameObject** 다. 즉 렌더링 성능 이득이 없다. Tilemap 도 같다.
- Unity 공식 `com.unity.2d.entities` 는 preview 0.31 에서 멈춘 옛날 패키지다. 지금 쓸 물건이 아니다.

그래서 실제로 쓰는 방법은 셋 중 하나다.

1. **NSprites** (`com.tonymax.nsprites`, OpenUPM / GitHub Antoshidza) — ComputeBuffer + `DrawMeshInstancedProcedural` 로 엔티티를 스프라이트처럼 그린다. 정렬·컬링·애니메이션·2D 트랜스폼까지 있다. 서드파티지만 관리되고 있다.
2. **직접 쿼드로 그리기** — 스프라이트를 쿼드 메시로 만들어 Forward+ 로 그린다. 2D 라이팅 등 URP 2D 기능은 포기.
3. **하이브리드** — 그림은 GameObject 로 두고 계산만 ECS 로. 스프라이트 렌더 성능 이득은 없다.

**즉 "최적화가 좋아서 DOTS 를 쓴다" 는 동기가 2D 스프라이트에서는 절반만 성립한다.** 계산(이동·AI·충돌)은 확실히 빨라지지만, 그리는 쪽은 공짜로 안 따라온다.

## 4. 선택지

### 안 A. 하이브리드 (권장)

- **인게임의 많이 도는 것**(적 떼, 총알, 타일 시뮬레이션)만 ECS.
- **아웃게임·UI·저장·씬 전환·오디오**는 지금 `기본구조.md` 그대로 (Master / Manager / Hub).
- 두 세계는 **싱글턴 컴포넌트 + 명령 큐**로만 이야기한다. Hub 에서 ECS 월드를 직접 만지지 않는다.
- 장점 : 문서를 버리지 않는다. UI·오디오처럼 DOTS 가 약한 데를 피한다.
- 단점 : 경계 규칙을 잘 정해야 한다. 안 정하면 제일 지저분해진다.

### 안 B. 전면 ECS

- `기본구조.md` 를 폐기하고 시스템/컴포넌트 규약 문서를 새로 쓴다.
- 장점 : 일관성. 로컬 LLM 에게 줄 규칙이 하나로 깔끔하다.
- 단점 : UI·오디오·씬 전환까지 ECS 로 짜는 건 고통이다. 2D 렌더도 직접 해결해야 한다.

### 안 C. ECS 보류

- 지금은 MonoBehaviour 구조로 가고, 스케일 문제가 실제로 터지면 그때 도입.
- 장점 : 지금 만들 툴(2D 그림 툴, 사운드 툴)에 집중할 수 있다.
- 단점 : 나중에 갈아엎는 비용. 다만 안 A 로 설계해두면 그 비용이 크게 준다.

## 5. 이 프로젝트 특유의 고려사항

`ProjectOfficina` 는 **게임이 아니라 키트**다. `기본구조.md` 는 대상 게임 프로젝트에 넣어줄 산출물이자 **로컬 Qwen 이 코드를 뽑을 때 지킬 뼈대**다. 그래서 두 가지가 더 걸린다.

- **키트는 "어떤 게임에든 끼운다" 가 목표인데, ECS 는 끼우는 게 아니라 프로젝트 전체를 규정한다.** 구조 템플릿을 **MonoBehaviour 판 / ECS 판 둘로 나누고 설정으로 고르게** 하는 편이 목표에 맞다.
- **ECS 는 보일러플레이트가 많다.** 이건 사람에겐 단점이지만 **로컬 LLM 에겐 오히려 유리**하다. 정형화된 반복 코드라 틀리기 어렵고, "규칙대로 도는 코드"라 합격 판정도 쉽다. 다만 Burst 제약(managed 타입 금지 등)을 컨벤션 문서에 못 박아둬야 한다.
