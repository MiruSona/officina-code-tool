# C# 포매터 대안 조사 — 취향대로 설정할 수 있는가

> 조사일 2026-08-20 · 이어지는 문서 : `Docs/Research/2026-08-20-코드컨벤션조사.md`
> 질문 : "서식을 CSharpier 처럼 자동으로 맞추되, 규칙을 내 취향대로 바꿀 수 있는 도구는 없나?"

---

## 결론 먼저

**있다. `dotnet format` + `.editorconfig` 조합이다.** 단, CSharpier를 고른 이유였던 "폴더만 지정해도 돈다"는 이 조합에서는 그대로 안 된다 — **대신 우회법을 이 PC에서 직접 확인했다** (아래 1-3절).

| 도구 | 폴더만으로 실행 | 취향 반영 범위 | 합격/불합격 판정 | 라이선스 | 설정 파일 이식성 |
| --- | --- | --- | --- | --- | --- |
| **CSharpier** (기존 선택) | ✅ 됨 (직접 확인은 이전 조사) | ⛔ 옵션 5개뿐 (줄 길이·탭·들여쓰기 칸수·줄바꿈 문자·XML 공백) — 중괄호 위치·공백 스타일은 못 바꿈 | `check` → 종료코드 1 | MIT | `.csharpierrc` 파일 하나 |
| **`dotnet format` + `.editorconfig`** | ⛔ 안 됨 (직접 확인, 아래) → **가짜 csproj 로 우회 가능** (직접 확인) | ✅ **매우 넓음** — 중괄호 위치, 공백 30여 종, 들여쓰기, 줄바꿈, `var` 사용, 패턴 매칭 스타일, 이름 규칙까지 전부 `.editorconfig` 한 파일에 | `--verify-no-changes` → 종료코드 2 (직접 확인) | MIT (.NET SDK 포함) | `.editorconfig` 파일 하나 (+ 가짜 csproj 1개) |
| **ReSharper `cleanupcode`** | ⚠️ 파일 단위로는 되지만 **서식만** 됨. 이름 규칙 등 전체 정리는 솔루션 필요 | ✅ 넓음 (`.DotSettings`) | ⛔ 전용 판정 플래그 없음. `git diff` 로 우회해야 함 | **무료** (2013년부터, 라이선스 키 불필요) | `.DotSettings` 파일 하나, 단 전체 기능은 `.sln` 필요 |
| **astyle** | 됨 | ⚠️ 중괄호·공백·들여쓰기 수준. C# 전용 규칙(이름, `var`, 패턴 매칭)은 개념 자체가 없음 | 없음 (스크립트로 diff 확인) | MIT | 설정 파일 1개 |
| **uncrustify** | 됨 | astyle 보다 옵션 많음, 단 C# 전용 규칙 없음 | 없음 | **GPL-2.0** | 설정 파일 1개 |

**권장 : `dotnet format` + `.editorconfig`로 바꾼다.** 이유:
1. **취향을 반영할 수 있는 유일한 후보다.** 중괄호 위치, 공백, `var` 사용 여부까지 전부 `.editorconfig` 한 파일로 정할 수 있다는 게 Microsoft 공식 예제 파일로도, 이 PC에서의 실제 실행으로도 확인됐다.
2. **CSharpier의 장점(폴더만 지정)을 흉내 낼 수 있다.** Unity 프로젝트 파일에 의존하지 않는 **가짜 서식용 csproj**를 하나 두면(아래 1-3절) 된다. `UnityEngine`, `MonoBehaviour`처럼 정의되지 않은 타입이 있어도 서식은 문제없이 걸렸다 — 서식 검사는 코드를 실제로 컴파일하는 게 아니라 문법 구조만 읽기 때문이다.
3. **취향과 자동화는 안 부딪힌다.** 취향(중괄호 위치 등)을 누가 정하든, 로컬 LLM이 쓴 코드는 어차피 포매터가 사후에 고쳐 준다. 취향을 넣는다고 로컬 LLM이 더 자주 틀리게 되는 게 아니다.
4. **ReSharper는 차선책으로 남긴다.** 무료인 건 확실하지만, 전용 "검사만" 플래그가 없어 CI 판정에 `git diff` 같은 우회가 필요하고, 전체 기능은 결국 Unity가 다시 만드는 `.sln`에 기대야 한다 — CSharpier를 고른 바로 그 이유(Unity 프로젝트 파일 불안정성)에 다시 걸린다.
5. **astyle/uncrustify는 제외한다.** C#을 "지원"은 하지만 진짜 C# 문법을 이해하는 게 아니라 중괄호·공백만 보는 범용 도구라 `var`, 패턴 매칭, 이름 규칙 같은 걸 다루지 못한다. uncrustify는 라이선스도 GPL-2.0이라 더 불리하다.

**중요한 구분 (아래에서 자세히)** : 이전 조사에서 나온 "Unity가 `.editorconfig`를 무시한다"는 건 **Unity 에디터 안에서 코드를 컴파일할 때** 얘기다. `dotnet format`을 **Unity 밖에서 CLI로** 돌리는 이번 얘기와는 완전히 다른 층이다. 헷갈리면 안 된다.

## 1. `dotnet format` — 지금 버전(.NET SDK 9.0.306) 기준 직접 확인

이 PC에 `.NET SDK 9.0.306`이 설치돼 있어 **추측이 아니라 직접 실행해서 확인했다.**

### 1-1. 폴더만 지정하면 — 안 된다 (직접 확인)

빈 폴더에 `.cs` 파일 하나만 두고 실행:

```
$ dotnet format --verify-no-changes .
Unhandled exception: System.IO.FileNotFoundException:
'...'에서 MSBuild 프로젝트 파일 또는 솔루션 파일을 찾을 수 없습니다.
<workspace> 인수를 사용하여 사용할 파일을 지정하세요.
```

`dotnet format --help`도 확인했다 — 명령 형태는 `dotnet-format [<PROJECT | SOLUTION>] [command] [options]`뿐이고, **`--folder` 옵션 자체가 지금 버전 도움말에 없다.**

**과거엔 있었다는 이야기가 맞다.** [`dotnet/format` 저장소 이슈 #1385](https://github.com/dotnet/format/issues/1385) (2021-10-14 등록, 아직 열려 있음)에 따르면 **독립 실행형 5.1 버전**에서는 `--folder`가 폴더 자체를 대상으로 삼아 제대로 됐는데, **.NET 6부터 SDK에 내장된 버전**은 폴더만 줘도 그 안에서 csproj/sln을 찾으려 든다. 이 차이가 **의도적으로 없앤 건지 버그인지조차 이슈에서 답이 안 났고, 2026-08 현재도 미해결이다.**

### 1-2. `.editorconfig`로 얼마나 세밀하게 정할 수 있나 — 직접 확인, 매우 넓다

실제로 `.csproj` + `.editorconfig`를 두고 실행해봤다.

```ini
# .editorconfig
csharp_new_line_before_open_brace = none   # 중괄호를 같은 줄에
indent_size = 2
```

```csharp
// 실행 전
public class Test
{
    public int X = 1;
}

// dotnet format 실행 후 — 실제로 이렇게 바뀜
public class Test {
  public int X = 1;
}
```

`dotnet/docs`(CC-BY-4.0) 공식 예제 파일을 보면 `.editorconfig`의 `csharp_*` 규칙은 카테고리가 이렇게 나뉜다.

| 분류 | 예시 |
| --- | --- |
| 줄바꿈 (New line) | `csharp_new_line_before_open_brace` (중괄호 위치), `csharp_new_line_before_else` |
| 들여쓰기 (Indentation) | `csharp_indent_case_contents`, `csharp_indent_labels` |
| 공백 (Space) — **30여 개** | `csharp_space_after_cast`, `csharp_space_around_binary_operators`, `csharp_space_before_open_square_brackets` 등 |
| 줄 유지 (Wrapping) | `csharp_preserve_single_line_blocks` |
| 언어 스타일 | `csharp_style_var_for_built_in_types`(`var` 쓸지), `csharp_style_prefer_switch_expression`(패턴 매칭 선호) 등 |
| 이름 규칙 | `dotnet_naming_rule.*` (PascalCase, `I` 접두사 등) |

즉 **"중괄호를 같은 줄에 둘지, 줄 바꿔 둘지"부터 "`var`를 쓸지 타입을 그대로 쓸지"까지 전부 여기서 정한다.** CSharpier가 못 건드리는 영역이다.

### 1-3. "폴더만 지정" 문제 — 가짜 csproj로 우회 가능함을 직접 확인

`dotnet format`이 요구하는 건 **MSBuild가 "로드할 수 있는" 프로젝트 파일**이지, 그 프로젝트가 실제로 컴파일에 성공해야 하는 게 아니다. 그래서 다음을 직접 실행해 확인했다.

```xml
<!-- Format.csproj — Unity의 진짜 csproj가 아니라 서식 전용 껍데기 -->
<Project Sdk="Microsoft.NET.Sdk">
  <PropertyGroup><TargetFramework>net8.0</TargetFramework></PropertyGroup>
</Project>
```

이 옆에 `UnityEngine`, `MonoBehaviour`처럼 **실제로는 정의되지 않은 타입을 쓰는 파일**을 넣고 돌렸다.

```csharp
using UnityEngine;
public class Broken : MonoBehaviour
{
    public   int   Y   =   2;   // 공백이 지저분함
    void Start(){ SomeUndefinedThing(); }  // 존재하지 않는 메서드 — 컴파일 안 됨
}
```

```
$ dotnet format --verify-no-changes .
...error WHITESPACE: 공백 서식을 수정하세요...
EXIT=2
```

**컴파일이 안 되는 코드인데도 서식 검사·수정은 문제없이 됐다.** `var` 관련 규칙(의미 분석이 필요한 규칙)도 `int` 같은 내장 타입에서는 똑같이 동작했다 (`dotnet format style` 로 확인, `IDE0007` 경고가 정확히 뜸).

**이게 의미하는 것** : Unity가 만드는 진짜 `.csproj`에 기대지 않고, **Scripts 폴더를 통째로 긁어오는 가짜 `Format.csproj` 하나만 스튜디오 키트에 넣어 두면** `dotnet format`을 CSharpier와 거의 같은 방식으로("폴더 지정하듯") 쓸 수 있다. `.csproj`가 재생성되며 깨지는 Unity 특유의 문제도 피한다 — 이 가짜 프로젝트는 Unity가 건드리지 않는 별도 파일이기 때문이다.

**주의 — 확인 못 한 부분** : 이건 파일 3개짜리 장난감 예제로 확인한 거다. 실제 Unity `Assets/Scripts` 폴더(수백 개 파일, 여러 `.asmdef`, `Editor`/`Tests` 폴더 등 특수 폴더 포함)에서 이 가짜 csproj가 그대로 통하는지, 속도가 얼마나 나는지는 안 재봤다.

### 1-4. 합격/불합격 판정

`--verify-no-changes`를 붙이면 고칠 게 있을 때 **종료코드 2**로 끝난다 (CSharpier는 1). 스크립트에서는 "0이 아니면 실패"로 짜면 되니 문제없다. 붙이지 않으면 그 자리에서 고치고 종료코드 0을 낸다.

## 2. JetBrains ReSharper Command Line Tools — `cleanupcode`

- **완전 무료, 라이선스 키 불필요.** 2013년 7월부터 독립 실행형 무료 도구로 제공돼 왔고 지금도 그렇다. Rider나 Visual Studio 라이선스와 무관하게 쓸 수 있다.
- **설치** : `dotnet tool install -g JetBrains.ReSharper.GlobalTools` (NuGet, .NET 글로벌 도구). Windows 포함 크로스플랫폼.
- **폴더/파일만 지정 가능하나** : `cleanupcode File1 File2 ...` 처럼 **파일 목록**은 솔루션 없이도 된다. 단 이 경우 **서식만** 고친다 — 공식 문서 표현으로 "솔루션 없이 파일만 주면 선택한 정리 프로필과 무관하게 파일 단위로만 서식을 고친다. 다른 정리 작업(구문 스타일 적용 등)을 하려면 솔루션이 필요하다." **즉 이름 규칙 강제 같은 걸 하려면 결국 `.sln`이 있어야 한다** — Unity가 다시 만드는 그 `.sln`이다.
- **설정 파일** : `--settings="경로\My.DotSettings"`로 지정. 지정 안 하면 `솔루션이름.sln.DotSettings`를 자동으로 찾는다. `.DotSettings`는 XML 계열 단일 파일이라 다른 저장소로 그대로 옮길 수 있다.
- **프로필** : 내장 3종 — `Reformat Code`(서식만), `Reformat & Apply Syntax Style`(서식 + `var` 등 스타일), `Full Cleanup`(전부, 파일 헤더 갱신 제외).
- **합격/불합격 판정** : **전용 플래그가 없다.** 공식 문서가 권하는 방법은 "Git 관리 중이면 실행 후 `git diff`로 확인하라"다. 즉 **일단 파일을 고쳐놓고 나서** 바뀌었는지 사후 확인하는 방식이라, CSharpier의 `check`나 `dotnet format`의 `--verify-no-changes`처럼 "고치지 않고 검사만"이 안 된다. CI에 넣으려면 우회 스크립트(원본 백업 → 돌리기 → diff → 되돌리기)가 필요하다.

**정리** : 취향 반영은 넓지만, ① CI 판정 방식이 한 단계 불리하고 ② 전체 기능이 결국 Unity의 `.sln`에 기댄다는 점에서 `dotnet format`보다 이점이 적다. "가짜 csproj" 같은 우회도 통하는지는 확인 못 했다(3절 참고).

## 3. `.editorconfig` + Roslyn 포매터 — 사실상 1절과 같은 얘기

`.editorconfig`는 그 자체로 도구가 아니라 **설정 파일 포맷**이다. 이걸 읽어서 실제로 코드를 고치는 건 `dotnet format`(1절)이거나, IDE(Visual Studio/Rider/VS Code)의 "코드 정리" 기능이다. IDE 쪽은 사람이 에디터에서 저장할 때 켜지는 것이라 **자동화 스크립트(`format.ps1`)의 합격 판정 수단으로는 못 쓴다.** 그래서 이 조합에서 실질적인 CLI 도구는 결국 `dotnet format` 하나뿐이다 — 1절 내용을 그대로 참고하면 된다.

## 4. astyle / uncrustify — C# "지원"의 실제 의미

둘 다 C, C++, C#, Java 등 여러 언어를 다루는 **범용 코드 정리기**다. C# 파일도 받아주긴 하지만, 이 도구들은 **C#을 진짜로 이해하는 게 아니라 중괄호·괄호·공백 같은 토큰만 보고 줄바꿈/들여쓰기를 맞추는 방식**이다. Roslyn 기반인 CSharpier·`dotnet format`처럼 `var` 사용, 패턴 매칭 스타일, 이름 규칙 같은 **C# 고유 규칙은 애초에 다루는 개념 자체가 없다.**

| | astyle | uncrustify |
| --- | --- | --- |
| 라이선스 | MIT | **GPL-2.0** |
| 최근 릴리스 | 3.6.7 (2025-02-26) — 유지되는 편 | 확인 못 함 (커밋은 계속 있음) |
| 옵션 수 | 90여 개, 중괄호 스타일 15종 | astyle보다 훨씬 많음, 그만큼 복잡 |
| C# 전용 규칙 | 없음 | 없음 |

**판정** : 후보에서 제외. C#에 한정하면 `dotnet format`/CSharpier가 이미 훨씬 정교하고, 이 둘은 원래 C/C++용으로 만들어진 도구를 C#에 얹은 것이라 이점이 없다. uncrustify는 라이선스도 GPL이라 더 불리하다.

## 5. Unity 함정 재확인 — 두 층을 섞으면 안 된다

이전 조사(코드컨벤션조사.md 3-1절)의 "Unity가 `.editorconfig`를 무시한다"는 결론은 **여전히 유효하다. 단 적용 범위가 다르다.**

| 층 | 언제 동작하나 | `.editorconfig` 적용되나 |
| --- | --- | --- |
| **Unity 에디터 내부 컴파일** (analyzer가 에디터 안에서 실시간으로 도는 것) | Unity 실행 중 | ⛔ **무시됨.** Unity 이슈 트래커에 등록, Won't Fix로 닫힘 (이전 조사에서 확인) |
| **`dotnet format` CLI 실행** (이번 조사 대상) | Unity 밖, 터미널에서 `format.ps1` 실행 시 | ✅ **적용됨.** 이번 조사에서 직접 실행해 확인 |

**결론 : 이름 규칙·서식 규칙을 Unity 에디터 안에서 실시간으로 강제하고 싶으면 `.globalconfig`(이전 조사 방식)를 쓰고, 밖에서 CLI로 검사·수정하고 싶으면 `.editorconfig` + `dotnet format`을 쓴다. 이번 조사는 후자만 다룬다.** 둘을 같은 걸로 착각하면 "`.editorconfig` 아무 효과 없다"는 잘못된 결론에 이른다.

## 6. 설정 가능성과 유지비 — 맞바꿈 정리

취향을 반영할수록 **그 취향을 정하고 관리하는 사람**이 필요하다. 이 프로젝트는 1인 + AI다.

- `.editorconfig`는 **한 번 정하면 그 뒤로는 사람 손이 안 간다** — 포매터가 계속 그 기준으로 자동으로 고쳐 준다. "취향을 넣었으니 매번 검토해야 한다"는 아니다.
- 다만 **"고민할 옵션이 존재한다" 자체가 비용이다.** CSharpier는 "고를 게 없어서" 이 고민 자체를 없앴다. `.editorconfig`로 가면 중괄호 위치 하나만 해도 결정을 내려야 한다. **이번 조사 범위 밖이지만, 실제로 도입하려면 "우리 취향"을 정하는 짧은 결정 단계가 한 번 더 필요하다.**

## 7. 확인 못 한 것

- **가짜 `Format.csproj`가 실제 Unity `Assets/Scripts` 규모(수백 파일, 여러 `.asmdef`)에서도 통하는지.** 이번엔 파일 3개짜리 장난감 예제로만 확인했다.
- **가짜 csproj 방식이 `ReSharper cleanupcode`에도 통하는지.** `dotnet format`에서만 확인했다.
- **`dotnet format`의 종료코드가 항상 2인지, 상황마다 다른 코드를 내는지.** 이번엔 whitespace 위반 한 가지 상황만 확인했다.
- **`.editorconfig`와 `.globalconfig`를 같은 저장소에 같이 뒀을 때 어느 쪽이 우선하는지** — 이전 조사에서도 확인 못 했고 이번에도 못 했다.
- **uncrustify의 정확한 최근 릴리스 날짜.** 커밋 수만 확인했고 릴리스 태그는 못 봤다.
- **astyle/uncrustify가 실제로 최신 C# 문법(레코드, 원시 문자열 리터럴 등)에서 깨지는 사례가 있는지.** 검색으로 직접적인 사례를 못 찾았다. "토큰 기반이라 위험할 것"은 구조상 추론이지 확인된 사실이 아니다.
- **ReSharper `cleanupcode`의 우회 판정 스크립트(백업 → 실행 → diff → 복원)를 실제로 짜서 돌려보진 않았다.** 문서 근거로만 판단했다.
- WebSearch는 이번 조사에서 정상 동작했다. 막힌 곳 없음.
