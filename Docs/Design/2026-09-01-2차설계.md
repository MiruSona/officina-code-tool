## 1. Init / Process 순서

### 결정

순서는 **`~Master` 에 적힌 등록 순서 그대로**다. 대신 초기화를 `Init` / `PostInit` **2단계**로 쪼갠다.
부팅은 4패스로 돈다.

1. 전원 `new`
2. 전원 `Init` — **자기 것만** 챙긴다. `Hub.Get` 금지
3. 전원 Hub 에 등록
4. 전원 `PostInit` — **`Hub.Get` 은 여기서만.** 꺼낸 것은 필드에 캐싱

### 근거

순서 문제의 90% 가 "Init 중에 남을 꺼내려는데 아직 등록이 안 됐다" 이다. 단계를 나누면 **문제 자체가 없어진다.**
그리고 순서를 알고 싶으면 **Master 파일 하나만 열면 된다.**

### 버린 대안

- `[Order(100)]` 같은 속성 — 숫자 끼워넣기 전쟁이 벌어지고, 전체 순서가 한눈에 안 보인다.
- 위상 정렬 — 의존 선언과 순환 검사가 붙어 복잡해진다. DI 를 뺀 것과 같은 이유다.

### 뼈대

```csharp
public interface IManager : IDisposable
{
    void Init();       // 자기 것만. Hub.Get 금지
    void PostInit();   // 전원 등록 뒤. Hub.Get 은 여기서만
}
public interface IProcess      { void Process(float deltaTime); }
public interface IFixedProcess { void FixedProcess(float deltaTime); }
public interface ILateProcess  { void LateProcess(float deltaTime); }
```

Process 3종을 `IManager` 에서 뺀 이유는 둘이다. 안 쓰는 Manager 가 **빈 함수를 달지 않고**, 매 프레임 도는 **목록이 짧아진다.**
등록할 때 `is IProcess` 로 갈라 담는다.

## 2. Agent vs Util (이름 바꿈 : Handler → Util)

### 결정

- **상태를 들고 주인에게 1:1 로 붙으면 `~Agent`.**
- **무상태 함수 모음이면 `~Util`** 이고, 실제로 **`static class` 로 선언한다.**

판정은 3줄이다.

1. 인스턴스 필드가 있나 → Agent
2. 생성자가 owner 를 받나 → Agent
3. 둘 다 아니면 Util (`static class`)

### 근거

이름을 `Handler` 에서 `Util` 로 바꾼 이유는, Handler 가 "이벤트에 반응해 처리하는 놈" 으로 읽혀 오해를 부르기 때문이다.
`Util` 은 "무상태 static 함수 모음" 이라는 규칙을 **이름이 자기를 설명한다** (C# `Path`, Unity `Mathf` 계열).

경계 규칙 하나 : **캐시나 공유 상태를 들고 싶어진 Util 은 층을 올려 Manager 나 Service 로 만든다.**
최하층에 공유 상태가 숨는 것을 막는 게 진짜 목적이다.

### 버린 대안

"무게로 가른다" (가벼우면 Util, 무거우면 Agent) — 주관이라 AI 가 매번 다르게 판정한다.

### 뼈대

```csharp
public sealed class ViewAgent            // 상태 O, owner 받음
{
    public ViewAgent(MonsterObject owner) { }
}
public static class SpriteColorUtil      // 상태 X — static class 가 곧 규칙
{
    public static void SetAlpha(SpriteRenderer target, float a) { }
}
```

## 3. Hub.Get 실패

### 결정

`Get<T>()` 는 **예외를 던진다** (`HubNotFoundException`). 메시지에는 **찾던 타입 · Hub 이름 · 지금 등록된 목록**을 담는다.
없을 수도 있는 경우에만 `TryGet<T>(out T)` 를 쓴다. **중복 등록도 예외**다.

### 근거

null 을 돌려주면 세 층 아래에서 NullReference 로 터져 **원인 자리가 안 보인다.** 예외는 터진 자리가 곧 원인 자리다.
컨벤션 2-5(`?.` · `??` 자제)와도 맞물린다.

### 버린 대안

- null 반환.
- Null Object 패턴 — 아무 일도 안 일어나면서 예외도 안 나니 제일 나쁘다.

### 뼈대

```csharp
public static class InGameHub
{
    public static T    Get<T>()        where T : class;   // 없으면 throw
    public static bool TryGet<T>(out T hub) where T : class;
    public static void Register<T>(T hub, object owner) where T : class;  // 중복이면 throw
    public static void UnregisterAllBy(object owner);
}
```

Hub 는 `static class` 라 상속으로 공유가 안 된다. 그래서 내부는 인스턴스 `HubTable`(Dictionary + owner 목록)에 **얇게 위임**한다 — 새 Hub 를 만들 때 복붙할 게 5줄이다.

`Get` 은 매 프레임 부르지 않고 **`PostInit` 에서 캐싱**한다 (1번과 짝).

## 4. Process 도는 중에 목록이 바뀌는 것

### 결정

**버퍼 두 개 + 즉시 죽음 표시.**

- **추가** : 추가 버퍼에 넣고 순회가 끝날 때 합류시킨다. **다음 프레임부터 돈다.**
- **삭제** : 삭제 버퍼에 넣으면서 그 항목에 **dead 표시를 즉시** 한다. 순회는 표시를 보고 건너뛴다.
- 실제 제거 · 풀 반납 · 뒷정리는 **순회가 끝난 뒤** 삭제 버퍼로 처리한다.

이 로직은 **`ProcessList<T>` 클래스 하나로 못 박고** GameRunner · Master · Manager 가 전부 그것만 쓴다.
세 군데가 각자 짜면 같은 버그를 세 번 만든다.

### 근거

- 즉시 완전 제거는 순회 중 리스트 변경이다 — 인덱스가 밀리거나 예외가 난다.
- 표시 없이 버퍼만 쓰면 **순회 뒤쪽의 죽은 항목이 같은 순회에서 한 번 더 돈다.**
- 매 프레임 복사본 순회는 Update 안 할당이라 뺀다.

곁들인 규칙 : **씬 전환 요청도 즉시 실행하지 않고 프레임 끝 한 번으로 미룬다** (GameMaster 쪽 규칙).

### 뼈대

```csharp
public sealed class ProcessList<T> where T : class
{
    public void Add(T item);        // 순회 중이면 추가 버퍼로
    public void Remove(T item);     // 즉시 dead 표시 + 삭제 버퍼, 실제 제거는 순회 끝
    public void ProcessAll(float deltaTime);
    public void FixedProcessAll(float deltaTime);
    public void LateProcessAll(float deltaTime);
}
```

## 5. Manager 하나가 두 Hub 에 걸칠 때

### 결정

**금지한다.** 등록하는 Hub 는 **소유 Master 의 Hub 하나뿐**이다.
남의 Hub 것은 등록하지 말고 **꺼내 쓴다** (Hub 는 static 이라 어디서든 `Get` 할 수 있다).

인게임 · 아웃게임 양쪽에서 **늘** 필요하면 그건 Manager 가 아니라 **Service** 다. `GlobalHub` 에만 등록한다.

### 근거

다중 등록은 **소유 Master 가 죽은 뒤 유령 참조를 남겨** 3번의 예외 정책을 무력화한다.
`Get` 이 던지지 않고 **죽은 객체를 돌려주는 것**이 제일 나쁜 실패다.

등록 API 가 owner 를 받으므로 `Master.OnDestroy` 는 `UnregisterAllBy(this)` 한 줄로 끝난다.

### 버린 대안

- 다중 등록 + 선등록 우선 — 주인이 코드에 안 보인다.
- Hub 통합 — 씬 생명주기가 섞인다.

## 6. `~Object` 만드는 경로

### 결정

- **`Instantiate` 를 부르는 곳은 전역 ResourceService 한 곳뿐.**
- Manager(예: `NpcManager`)는 스폰 판단 · 목록 · 수명 관리를 다 하되, **생성만** `Rent(PrefabKeys.X, parent)` / `Return(obj)` 로 부른다.
- 프리팹 키는 **코드 상수(`PrefabKeys`)** — 오타는 컴파일이 잡고, 쓰임새는 grep 으로 다 찾힌다.
- 로드는 `Resources.Load` 로 시작하되 **`IPrefabSource` 한 겹**을 끼워 나중에 갈아끼울 수 있게 한다 (Addressables 는 뺐지만 길만 남긴다, 비용 0).
- **풀링 범위는 전원 풀링** (사용자 확정) — 모든 Object 가 `Rent` / `Return` 만 쓴다.

전원 풀링인 이유 : 규칙이 하나라 AI 가 안 헷갈리고, Unity 에서 `Instantiate` / `Destroy` 반복이 GC 스파이크의 주범이다.
메모리가 남는 것은 씬이 끝날 때 Master 가 `ClearPool` 로 푼다.

**함정** : 풀 반납은 Destroy 가 아니라서 **`OnDestroy` 가 안 불린다.** 정리 코드는 **`OnReturn()`** 에 둔다.

### 버린 대안

- SO 카탈로그에 프리팹 참조 — SO 는 수치 통으로만 쓰기로 했다.
- 옵트인 풀링 — 풀 대상인지 매번 판단해야 하고 정리 코드가 두 갈래가 된다.

### 뼈대

```csharp
public interface IResourceHub
{
    T    Rent<T>(string key, Transform parent) where T : Component;
    void Return<T>(T instance) where T : Component;
    void ClearPool(string key);
}
public interface IPrefabSource { GameObject Load(string key); }   // Resources 구현으로 시작
public interface IPooledObject { void OnRent(); void OnReturn(); }
public static class PrefabKeys { public const string Monster = "Prefabs/Monster"; }
```

## 7. Manager 끼리 알리는 길

### 결정

**중앙 EventBus** (사용자 확정). 타입 기반 · 동기 즉시 호출이다.
**Hub 에는 알림 기능을 넣지 않는다** — pull 전용으로 남긴다.

붙는 규칙 4줄.

1. 이벤트는 **`readonly struct`** — 박싱도 할당도 없다.
2. **동기 즉시 호출**, 큐잉 없음.
3. 구독은 `PostInit`, 해제는 `Dispose`.
4. **핸들러 안에서 다시 `Publish` 금지** (재진입).

### 버린 대안

- 직접 event 구독(B안) — 상호참조와 참조 순서가 꼬이고, 상대가 없는 씬마다 `TryGet` 분기가 생기며, 구독 해제 하나를 빠뜨리면 **죽은 Manager 가 계속 불린다.**
- 섞어 쓰기 — 매번 "버스냐 직접이냐" 를 판단하게 된다. 금지한다.

### 뼈대

```csharp
public static class EventBus
{
    public static void Publish<T>(in T e) where T : struct;
    public static IDisposable Subscribe<T>(object owner, Action<T> handler) where T : struct;
    public static void UnsubscribeAllBy(object owner);
}
public readonly struct PlayerDiedEvent { public readonly int ObjectId; }
```

## 8. 서로 얽힌 곳

| 얽힘 | 내용 |
| --- | --- |
| 1 ↔ 3 | `Hub.Get` 을 **`PostInit` 에서만** 불러야 "못 찾으면 던진다" 가 성립한다. `Init` 에서 부르면 정상 상황에도 던진다 |
| 5 → 3 | 다중 등록을 금지해야 유령 참조가 없어 예외 정책이 산다 |
| 5 = 7 | `UnregisterAllBy(owner)` 와 `UnsubscribeAllBy(owner)` 는 **같은 owner 개념**이다. `Master.OnDestroy` 두 줄, 한 헬퍼로 묶는다 |
| 4 ↔ 6 | Spawn / Despawn 은 대부분 Process 도중이다. 새 Object 는 **다음 프레임부터**, 풀 반납은 **반드시 순회가 끝난 뒤**. 순회 중에 반납하면 **같은 프레임에 다른 Manager 가 같은 인스턴스를 다시 빌려간다** |
| 2 → 6 | 풀에서 나올 때 **Agent(상태 O)는 `OnRent` 에서 리셋**이 필요하고, **Util(무상태)은 손댈 것이 없다** |
| 1 → 4 | Process 인터페이스가 3종으로 갈렸으니 `ProcessList` 도 3개이거나 1개 + 검사다. **뼈대 코드를 쓸 때 정한다** |
